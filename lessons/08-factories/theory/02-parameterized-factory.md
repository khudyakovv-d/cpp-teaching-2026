# Одна фабрика с выбором типа

В первой части мы выбирали объект `FactoryA` или `FactoryB`, затем вызывали одинаковый `create()`. Теперь перенесём выбор в аргумент одного метода. Определения `Product`, `ProductA` и `ProductB` сохраняются.

## Как представить выбор

Для двух вариантов заведём отдельный тип:

```cpp
enum class ProductType { A, B };
```

`enum class` объявляет перечисление. Его именованные значения записываются как `ProductType::A` и `ProductType::B`. Так параметр функции явно означает выбор продукта. Запись `factory.create(1)` не скомпилируется: обычное число не преобразуется в это перечисление неявно.

Здесь слово «тип» означает метку выбора во время выполнения. Это обычный аргумент метода, а не параметр C++ `template`.

## Выбор через switch

Для исключения нужен `<stdexcept>`, для создания — `<memory>`:

```cpp
class ParameterizedFactory {
public:
    std::unique_ptr<Product> create(ProductType type) const {
        switch (type) {
        case ProductType::A:
            return std::make_unique<ProductA>(10);
        case ProductType::B:
            return std::make_unique<ProductB>("demo", 2);
        }
        throw std::invalid_argument("Unknown product type");
    }
};
```

У каждой ветви свой вызов конструктора. Разные сигнатуры продуктов снова не мешают общему возвращаемому типу: указатель на конкретный продукт передаётся как `std::unique_ptr<Product>`.

В этом варианте фабрика сама выбирает начальные параметры: `10` для первого продукта, `"demo"` и `2` для второго. Вызывающий код передаёт только метку:

```cpp
ParameterizedFactory factory;
auto first = factory.create(ProductType::A);
auto second = factory.create(ProductType::B);

std::cout << first->describe() << '\n';
std::cout << second->describe() << '\n';
```

Для этих строк нужен `<iostream>`. Вывод совпадёт с примером первой части:

```text
ProductA(value=10)
ProductB(text=demo, count=2)
```

Здесь объект `ParameterizedFactory` можно создать один раз при настройке приложения, а метку `ProductType` передавать для каждой операции. Например, первое обращение выбирает A, следующее — B. Полученный владелец остаётся у вызывающего кода; после выбора он использует общий интерфейс продукта.

Исключение после `switch` задаёт отказ для значения, которое не обслуживается ни одной ветвью. Это также полезно, если перечисление позднее расширили, а создание нового продукта ещё не добавили. Превращать произвольные числа или строки из внешнего ввода в метки следует отдельной проверяемой операцией.

## От аргумента программы до продукта

Пусть пользователь запускает `factories_demo a` или `factories_demo b`. Сначала проверим имя. Для строк и исключений нужны `<string>` и `<stdexcept>`:

```cpp
ProductType parseProductType(const std::string& name) {
    if (name == "a") {
        return ProductType::A;
    }
    if (name == "b") {
        return ProductType::B;
    }
    throw std::invalid_argument("Unknown product name: " + name);
}

void runSelectedProduct(const std::string& name) {
    const ProductType type = parseProductType(name);
    ParameterizedFactory factory;
    auto product = factory.create(type);
    useProduct(*product);
}
```

В `main(int argc, char** argv)` значение `argc` — число аргументов вместе с именем программы, `argv[1]` — первый пользовательский аргумент. После проверки `argc == 2` программа вызывает `runSelectedProduct(argv[1])`. Функция `useProduct()` использует общий интерфейс продукта. Полная точка входа находится в [main.cpp](../practice/main.cpp).

Таким образом, путь одного обращения выглядит как **строка → проверенная метка → фабрика → продукт → использование**. На macOS или Linux после сборки из папки практики:

```sh
./build/factories_demo a
```

Вывод:

```text
ProductA(value=10)
```

Для аргумента `b` создаётся `ProductB`. Для неизвестного имени `unknown` проверка бросает исключение до вызова фабрики. В `main` оно перехватывается: сообщение `Unknown product name: unknown` выводится в `std::cerr`, программа возвращает код `1`. Неизвестное имя и ошибка создания продукта — разные этапы, хотя оба сообщают об отказе исключениями.

## Что изменилось в устройстве

В первой части конкретный тип продукта определялся переопределением виртуального `create()` в наследнике фабрики. Здесь его определяет `switch` в одном классе. Для выбора продукта виртуальный метод фабрики не нужен. Виртуальным остаётся интерфейс самого продукта.

Такой вариант называют **простой фабрикой**, или **Simple Factory**. В этом занятии также используем название **параметризованная фабрика**, подчёркивая выбор через аргумент. Её следует отличать от Factory Method из первой части, который опирается на переопределение метода создания.

Для небольшого фиксированного набора продуктов один класс с явным выбором может быть удобен: все варианты создания видны рядом. Чтобы добавить `ProductC`, потребуется добавить значение перечисления и ветвь `switch`. Клиент, который использует полученный `Product`, при этом может остаться прежним.

Если начальные параметры должны настраиваться, их нужно откуда-то получить. Фабрика может хранить постоянные настройки в полях, а данные отдельной операции получать аргументами метода. Единый метод вида `create(type, value, text, count)` заставляет клиента передавать параметры, часть которых выбранному продукту не нужна. В разделе о реестре разобран отдельный пример разделения настроек и данных операции.

## В каких сценариях это удобно

**Общий случай:** конкретный продукт нужно выбирать по значению, известному во время выполнения: метке в запросе, настройке или команде пользователя. Программа управляет набором поддерживаемых вариантов и может собрать соответствие «метка — вызов конструктора» в одном месте. Вызывающий код передаёт выбор в фабрику и получает продукт с общим интерфейсом.

Признаки подходящей задачи:

- Нужный тип может меняться от одного обращения к другому, и его удобно передавать аргументом `create(type)`.
- Все поддерживаемые реализации известны модулю фабрики; при добавлении продукта допустимо изменить его код выбора.
- Логика создания достаточно проста, чтобы ветви одного `switch` оставались понятными. Отдельно заменять каждый создатель не требуется.

**Как пользоваться:** вызывающий код проверяет входные данные и получает метку типа. Затем вызывает одну фабрику с этой меткой и работает с результатом через `Product`. Например, последовательные обращения могут передать сначала `ProductType::A`, затем `ProductType::B`. Параметры конструкторов в нашем варианте задаёт сама фабрика.

**Пример:** пользователь выбирает CSV или JSON для выгрузки отчёта. Обработчик запроса переводит выбранный формат в метку, фабрика создаёт соответствующий экспортёр, а дальнейший код вызывает общий метод выгрузки. Форматы иллюстрируют общий случай выбора реализации по входному значению.

**Цена решения:** фабрика знает все конкретные классы и меняется при расширении набора. Это удобно для обозримого набора встроенных реализаций. Если способы создания должны предоставляться и настраиваться разными модулями, полезно вынести их в отдельные фабрики и зарегистрировать по ключам.

## Когда фабрика вообще нужна

Прямой `make_unique<ProductA>(10)` уместен, когда конкретный класс известен и создание простое. Объект фабрики становится полезен, когда выбор повторяется, требуется подмена способа создания или клиент должен получать разные реализации через общий интерфейс. Само добавление класса с названием `Factory` не делает программу удобнее: нужно понимать, какую зависимость он переносит.

**Проверьте себя:** где здесь выбирается конкретный класс? Понадобится ли наследник `ParameterizedFactory` для продукта B? На каком этапе отклоняется неизвестное имя? Что меняется при добавлении продукта C?

**Ответ:** выбор выполняет `switch` по аргументу `ProductType`; отдельный наследник фабрики не нужен. Неизвестное имя отклоняется при преобразовании строки в метку, до создания продукта. Для продукта C нужно расширить перечисление, код выбора и преобразование имени.
