# Задача 0а. Версия с одной целью

Здесь теория о [преобразовании исходного кода в программу](../../theory/01-source-to-executable.md) и [системах сборки](../../theory/02-build-systems-and-cmake.md) применяется к небольшому проекту. Это первая версия для демонстрации преподавателя. Все действия с CMake выполняются через интерфейс Visual Studio Code, без команд в терминале.

Если окружение ещё не готово, сначала воспользуйтесь [инструкцией по установке](../../../../environment-setup.md).

## Что находится в проекте

```text
01-single-target/
├── .vscode/           настройки Visual Studio Code
├── CMakeLists.txt     описание проекта
├── CMakePresets.json  готовая конфигурация сборки
├── main.cpp
├── module1.cpp
├── module1.h
├── module2.cpp
└── module2.h
```

Три `.cpp`-файла компилируются отдельно, а затем объединяются в одну программу.

Главный файл для CMake — `CMakeLists.txt`:

```cmake
cmake_minimum_required(VERSION 3.27)

project(lab0a LANGUAGES CXX)

add_executable(
    lab0a
    main.cpp
    module1.cpp
    module2.cpp
)

target_compile_features(lab0a PRIVATE cxx_std_20)
```

Он сообщает CMake:

1. проект использует C++;
2. результатом должна стать исполняемая программа `lab0a`;
3. для неё нужно скомпилировать три `.cpp`-файла;
4. компилятор должен поддерживать C++20.

Именованный результат сборки называется **целью**, или **target**. В этом проекте цель одна — исполняемая программа `lab0a`.

Заголовочные файлы подключаются через `#include`. Для сборки этого проекта перечислять их в `add_executable` необязательно.

Пресет — это сохранённый набор настроек CMake. В `CMakePresets.json` подготовлены два связанных пресета с отображаемым именем `Build`:

- пресет Configure задаёт каталог `build` и параметры подготовки проекта;
- пресет Build указывает, как собирать уже подготовленный проект.

Генератор в них не закреплён, поэтому при первом Configure его выбирает CMake. Конфигурация сборки называется `Debug`: она добавляет информацию, нужную отладчику, но сама по себе отладчик не запускает.

Файлы в `.vscode` выполняют три небольшие настройки: рекомендуют расширения C/C++ и CMake Tools, включают работу через пресеты и отключают автоматический Configure. Поэтому подготовка проекта не начнётся незаметно сразу после открытия папки.

## Первая сборка и запуск

Откройте через **File → Open Folder…** всю папку `01-single-target`. Если открыть только `main.cpp`, CMake Tools не увидит проект целиком.

Откройте палитру команд:

- Windows: `Ctrl+Shift+P`;
- macOS: `Cmd+Shift+P`.

Выберите `CMake: Select Configure Preset`, а затем пресет `Build`. Выбор пресета ещё не запускает сборку. После него выполните `CMake: Configure`.

Во время Configure, то есть подготовки сборки, CMake:

1. читает `CMakeLists.txt`;
2. находит компилятор;
3. выбирает генератор и соответствующую систему сборки;
4. создаёт для неё служебные файлы в каталоге `build`.

После Configure программы ещё нет. По содержимому `build` можно понять, какой генератор был выбран:

- `Makefile` — Make;
- `build.ninja` — Ninja;
- файл `.sln` — Visual Studio и MSBuild.

Обычно в Windows CMake выбирает генератор Visual Studio и систему MSBuild, а в macOS — генератор `Unix Makefiles` и систему Make. Выбор сохраняется в `build/CMakeCache.txt` и используется при следующих сборках.

Если позже понадобится другой генератор, его можно явно указать в пресете. После изменения нужно выполнить `CMake: Delete Build Directory and Reconfigure`: один каталог `build` нельзя переключать между разными генераторами.

Теперь нажмите **Build** в боковой панели CMake Tools или выберите `CMake: Build`. Если VS Code предложит выбрать Build Preset, укажите `Build`. Это действие запускает систему сборки: она вызовет компилятор для каждого `.cpp`, а затем линковщик.

Готовая программа находится внутри `build`:

- при Make или Ninja — обычно `build/lab0a` в macOS и `build/lab0a.exe` в Windows;
- при генераторе Visual Studio — обычно `build/Debug/lab0a.exe`.

Чтобы запустить программу, выберите цель `lab0a` в разделе **Launch** боковой панели CMake Tools и нажмите кнопку запуска. То же действие доступно через `CMake: Run Without Debugging`.

В терминале VS Code появится:

```text
Hello world!
John
James
John
James
James
```

Для запуска под отладчиком используется отдельное действие `CMake: Debug Target`. Пресет `Build` сам по себе отладчик не запускает.

## Проверяем раздельную компиляцию

После первой сборки найдите внутри `build` объектные файлы:

- в Windows — файлы `.obj`;
- в macOS — файлы `.o`.

Имена и расположение служебных папок зависят от генератора. Важно увидеть по одному объектному файлу для `main.cpp`, `module1.cpp` и `module2.cpp`.

Теперь измените только `module1.cpp`, сохраните файл и снова нажмите **Build**. В окне **Output** должны появиться два действия:

1. повторная компиляция `module1.cpp`;
2. повторная линковка `lab0a`.

`main.cpp` и `module2.cpp` не изменились, поэтому компилировать их повторно не нужно. Это и есть инкрементальная сборка.

## Разбираем пространства имён

В начале `main.cpp` вызываются функции с одинаковым коротким именем:

```cpp
Module1::getMyName();
Module2::getMyName();
```

Части `Module1::` и `Module2::` позволяют однозначно выбрать нужную функцию.

Затем появляется директива:

```cpp
using namespace Module1;
```

После неё строка **(A)** вызывает `Module1::getMyName()` и выводит `John`.

Если раскомментировать строки **(B)** и **(C)**, одновременно станут доступны две функции с именем `getMyName`. Компилятор не сможет выбрать одну из них и сообщит о неоднозначном вызове.

Устранить ошибку можно несколькими способами:

- написать полное имя функции: `Module1::getMyName()`;
- убрать одну из директив `using namespace`;
- импортировать только нужную функцию: `using Module2::getMyName;`.

Последний вариант используется перед строкой **(D)**. Поэтому она вызывает функцию из `Module2` и выводит `James`.

Чтобы писать `cout` вместо `std::cout`, можно импортировать конкретное имя:

```cpp
using std::cout;
```

Директива `using namespace std;` тоже убирает префикс `std::`, но одновременно импортирует множество имён. Это повышает риск конфликтов, поэтому лучше писать `std::cout` или импортировать только нужное имя.

## Показываем ошибку линковки

На демонстрации добавим ещё одну функцию `getMyName()`, которая возвращает `Peter`, и поместим её в новое пространство имён. Для неё понадобятся заголовочный файл с объявлением и `.cpp` с реализацией. Заголовок нужно подключить в `main.cpp`, а функцию — вызвать через полное имя пространства.

Сначала можно вызвать функцию, но не добавлять новый `.cpp` в `add_executable`. `main.cpp` успешно скомпилируется, потому что объявление функции есть в заголовке, а линковка завершится ошибкой: реализации функции нет среди объектных файлов. После добавления `.cpp` в `CMakeLists.txt` повторная сборка должна завершиться успешно и вывести `Peter`.

После демонстрации должно быть понятно:

1. почему каждый `.cpp` превращается в отдельный объектный файл;
2. зачем нужны заголовочные файлы и почему объявление не заменяет реализацию;
3. зачем после компиляции нужна линковка;
4. чем Configure отличается от Build;
5. почему после изменения одного `.cpp` остальные не компилируются повторно;
6. как пространства имён различают функции с одинаковыми именами.
