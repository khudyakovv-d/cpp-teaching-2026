# O — Open/Closed Principle

## Смысл принципа

**Принцип открытости/закрытости:** модуль должен быть открыт для расширения и закрыт для модификации. Практически это означает, что новое поведение подключается без изменения устойчивого алгоритма, который его использует. Сначала нужно определить, какие расширения ожидаются и какой код мы хотим от них защитить.

## Предметная ситуация

Магазин принимает заказы с самовывозом и курьерской доставкой. Затем подключает экспресс-доставку. У способов доставки разные тарифы, но итоговая сумма во всех случаях складывается из стоимости товаров и доставки.

Меняется набор тарифов, а правило сложения остаётся прежним. Поэтому расчёт заказа и способы вычисления стоимости доставки имеют естественную границу.

## Нарушение

Каждый новый способ доставки добавляется прямо в расчёт заказа:

```cpp
enum class Delivery { Pickup, Courier };

// Стоимость заказа и все варианты доставки меняются в одном месте.
int orderTotal(int goods, Delivery delivery, int kilograms) {
    switch (delivery) {
    case Delivery::Pickup:
        return goods;
    case Delivery::Courier:
        return goods + 200 + 30 * kilograms;
    }
    throw std::invalid_argument("Unknown delivery");
}
```

В примере стоимость задана небольшими целыми значениями в одной денежной единице, масса — неотрицательным целым числом килограммов. Поддерживаемые значения не переполняют `int`.

## Как проявится проблема

Появляется экспресс-доставка с тарифом `500 + 50 * kilograms`. Придётся добавить элемент перечисления и ветку в `orderTotal`. При каждом следующем тарифе опять меняется общий расчёт заказа, хотя его правило не изменилось. У новых тарифов и старой логики появляется общая область изменений и риск регрессии.

Один `switch` не доказывает нарушение OCP. Для небольшого закрытого набора вариантов это вполне разумное решение. Проблема нашего сценария в том, что набор доставок регулярно расширяется, а расширения вторгаются в устойчивый алгоритм.

## Переписываем

Выделим договор тарифа: для допустимой массы вернуть неотрицательную стоимость доставки в той же денежной единице. Конкретные тарифы реализуют этот договор:

```cpp
class DeliveryFee {
public:
    virtual ~DeliveryFee() = default;
    virtual int calculate(int kilograms) const = 0;
};

class Pickup final : public DeliveryFee {
public:
    int calculate(int) const override { return 0; }
};

class Courier final : public DeliveryFee {
public:
    int calculate(int kilograms) const override { return 200 + 30 * kilograms; }
};

int orderTotal(int goods, const DeliveryFee& delivery, int kilograms) {
    return goods + delivery.calculate(kilograms);
}

// Новый тариф добавлен без изменения orderTotal, Pickup и Courier.
class Express final : public DeliveryFee {
public:
    int calculate(int kilograms) const override { return 500 + 50 * kilograms; }
};
```

В этом фрагменте `Express` — именно новое расширение. После его добавления текст `orderTotal`, `Pickup` и `Courier` остаётся прежним.

Использование:

```cpp
const Express express;
std::cout << orderTotal(1000, express, 2) << '\n'; // 1600
```

Клиент передаёт тариф по ссылке; расчёт его не сохраняет и им не владеет.

## Где изменения всё-таки останутся

Чтобы воспользоваться `Express`, нужно создать его и передать в расчёт. Если способ доставки выбирает пользователь, код выбора или регистрации тоже изменится. **Закрыли от добавления тарифов конкретно `orderTotal`, а не всю программу.** Компиляция и повторные проверки по-прежнему нужны.

Исправлять ошибки в `orderTotal` можно. Менять его при изменении самого правила расчёта тоже можно. OCP защищает выбранную границу от определённого вида изменений, а не объявляет существующий код неприкосновенным.

## Что выиграли и сколько это стоит

Новый тариф локализован в собственной реализации. Цена — интерфейс, несколько классов и отдельное место выбора тарифа. Виртуальные методы здесь удобны благодаря уже знакомому полиморфизму; OCP также можно реализовать передачей функции или данными конфигурации. Наследование не является обязательной частью принципа.

Общий случай применения: устойчивый алгоритм использует изменяемое поведение с понятным договором. Не стоит заранее строить расширения для всех воображаемых требований.

**Проверьте себя:** изменение регистрации фабрики при добавлении `Express` означает, что OCP не соблюдён?

**Ответ:** нет. В данном решении от новых тарифов защищён расчёт заказа. Место подключения конкретных реализаций намеренно знает об их существовании.
