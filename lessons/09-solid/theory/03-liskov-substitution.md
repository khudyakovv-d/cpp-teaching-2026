# L — Liskov Substitution Principle

## Смысл принципа

**Принцип подстановки Лисковой:** код, принимающий указатель или ссылку на базовый класс, должен иметь возможность работать с объектом без необходимости выяснять его конкретный класс. Подтип сохраняет обещания базового типа, на которые опирается такой код.

Совпадения имён и сигнатур методов недостаточно. Важны результаты и допустимые изменения состояния. **Предусловие** описывает допустимые входные данные и состояние перед вызовом, **постусловие** — обещанный результат и состояние после него. Подтип не должен ужесточать предусловия или ослаблять постусловия базовой операции. **Инвариант** — условие, которое объект должен сохранять между публичными операциями. Также оговариваются допустимые отказы.

## Предметная ситуация

В редакторе схем можно менять ширину и высоту прямоугольника и узнавать его площадь. Затем появляется квадрат, у которого стороны должны оставаться равными. Возникает соблазн использовать наследование, поскольку математически квадрат — частный случай прямоугольника.

Но классы описывают ещё и операции изменения фигур. Прежде чем строить иерархию, нужно проверить совместимость их поведения.

## Сначала договор, затем иерархия

Наш `Rectangle` обещает независимое изменение сторон:

- После `setWidth(w)` ширина равна `w`, высота сохраняется.
- После `setHeight(h)` высота равна `h`, ширина сохраняется.
- `area()` возвращает произведение текущих сторон.

Для компактности используем небольшие неотрицательные целые размеры, произведение которых помещается в `int`. Проверки этой области входов в учебном коде опущены.

## Нарушение

Если просто унаследовать setter-методы, можно независимо изменить одну сторону и превратить квадрат в прямоугольник. Поэтому первая попытка сохранить квадрат — переопределить эти методы так, чтобы каждый из них менял обе стороны. Посмотрим, что это означает для клиента базового класса.

Разработчик рассуждает: «Квадрат — частный случай прямоугольника», и добавляет наследование. Для сохранения равенства сторон квадрат переопределяет оба setter-метода:

```cpp
class Rectangle {
public:
    virtual ~Rectangle() = default;
    // Договор: меняется только указанная сторона.
    virtual void setWidth(int value) { width_ = value; }
    virtual void setHeight(int value) { height_ = value; }
    int width() const { return width_; }
    int height() const { return height_; }
    int area() const { return width_ * height_; }

private:
    int width_ = 0;
    int height_ = 0;
};

class Square final : public Rectangle {
public:
    void setWidth(int value) override { setSide(value); }
    void setHeight(int value) override { setSide(value); }

private:
    void setSide(int value) {
        Rectangle::setWidth(value);
        Rectangle::setHeight(value);
    }
};

int resizeAndMeasure(Rectangle& rectangle) {
    rectangle.setWidth(4);
    rectangle.setHeight(5);
    return rectangle.area(); // По договору Rectangle ожидается 20.
}
```

Поля остаются закрытыми: квадрат изменяет стороны через методы базы. Вызовы с квалификатором `Rectangle::` выполняют именно реализацию базы и не возвращаются в переопределение. Программа компилируется, вызовы виртуальных методов работают. Но это ещё не означает корректную подстановку.

## Как проявится проблема

Для обычного прямоугольника `resizeAndMeasure` возвращает `20`. Для квадрата — `25`:

```cpp
Rectangle rectangle;
Square square;
std::cout << resizeAndMeasure(rectangle) << '\n'; // 20
std::cout << resizeAndMeasure(square) << '\n';    // 25
```

Вызов `setHeight(5)` у квадрата меняет также ширину. Клиент соблюдал договор базового типа, но получил поведение, которое этот договор исключает.

Если обойти это проверкой `dynamic_cast<Square*>` внутри клиента, клиент начнёт знать каждый исключительный подтип. Такая проверка скрывает проблему конкретного вызова, но не восстанавливает обещание `Rectangle`.

## Переписываем

Сохраним общую возможность измерять площадь, а операции изменения размеров оставим у конкретных типов:

```cpp
class Shape {
public:
    virtual ~Shape() = default;
    virtual int area() const = 0;
};

class Rectangle final : public Shape {
public:
    Rectangle(int width, int height) : width_(width), height_(height) {}
    void setWidth(int value) { width_ = value; }
    void setHeight(int value) { height_ = value; }
    int area() const override { return width_ * height_; }

private:
    int width_;
    int height_;
};

class Square final : public Shape {
public:
    explicit Square(int side) : side_(side) {}
    void setSide(int value) { side_ = value; }
    int area() const override { return side_ * side_; }

private:
    int side_;
};

int measure(const Shape& shape) { return shape.area(); }

int resizeAndMeasure(Rectangle& rectangle) {
    rectangle.setWidth(4);
    rectangle.setHeight(5);
    return rectangle.area();
}
```

Теперь `Rectangle` и `Square` независимо реализуют `Shape`. Договор `Shape::area()` — вернуть геометрическую площадь текущей фигуры без изменения её состояния; он не обещает независимых setter-методов. Разные площади разных фигур допустимы.

```cpp
Rectangle rectangle(1, 1);
Square square(5);
std::cout << resizeAndMeasure(rectangle) << '\n'; // 20
// resizeAndMeasure(square); // Не компилируется: Square не является Rectangle.
std::cout << measure(rectangle) << '\n'; // 20
std::cout << measure(square) << '\n';    // 25
```

Клиент `resizeAndMeasure` сохраняет исходную задачу: установить стороны прямоугольника в 4 и 5 и вернуть площадь 20. Он принимает `Rectangle&`, поэтому передать ему `Square` теперь нельзя на уровне типов. В демонстрационном проекте оба вызова записаны с квалификатором `good::`, чтобы обращаться именно к исправленной версии. Обещание менять квадрат как произвольный прямоугольник убрано из модели, а измерение через общий интерфейс `Shape` сохранено для обеих фигур.

## Что выиграли и сколько это стоит

Клиенты общего интерфейса могут доверять его договору. Цена — пересмотр иерархии и сигнатур клиентов, которым нужны специальные операции. Код изменения размеров больше не пытается обслужить несовместимые требования одним типом.

Общий случай применения: всякий раз, когда объект используется через базовый интерфейс. Ошибки LSP встречаются и без геометрии: например, подтип отвергает вход, который база обязуется принимать, или неожиданно меняет дополнительные данные.

Этот пример относится именно к **изменяемому прямоугольнику с таким договором setter-методов**. Решение о наследовании должно опираться на общность поведения, а при выбранном наборе операций прямоугольник и квадрат ведут себя по-разному. Для другого интерфейса отношение подтипов нужно анализировать заново.

**Проверьте себя:** достаточно ли добавить `override` во все методы, чтобы гарантировать LSP?

**Ответ:** нет. Компилятор проверяет переопределение, но поведенческие обещания нужно сформулировать и проверять отдельно. В [демонстрации](../practice/lsp.cpp) нарушение воспроизводится безопасно: результат `25` проверяется как ожидаемый признак ошибки проектирования, поэтому программа может показать и исправление.
