# I — Interface Segregation Principle

## Смысл принципа

**Принцип разделения интерфейсов:** классы не должны зависеть от контрактов, которых они не используют. Интерфейс должен выражать потребность клиента: лишние операции связывают его с чужими задачами и ограничивают выбор подходящих реализаций.

Поэтому границы интерфейсов выбирают по тому, какие возможности нужны разным группам клиентов. При этом одна реализация может предоставлять несколько таких интерфейсов.

## Предметная ситуация

В офисной программе есть две задачи: печатать отчёты и сканировать документы. Сначала используется МФУ, которое умеет и то и другое. Позже для печати отчётов покупают отдельный принтер. Задача печати осталась прежней, и наличие сканера для неё не имеет значения.

«Клиент» здесь — функция или класс, использующие устройство. Поэтому важно посмотреть на зависимости функций `printReport` и `scanDocument`, а не только на набор методов самого устройства.

## Нарушение

Оба клиента принимают общий `OfficeDevice`. Работу оборудования имитируем выводом в поток и возвратом фиксированного текста скана:

```cpp
class OfficeDevice {
public:
    virtual ~OfficeDevice() = default;
    virtual void print(const std::string& text) = 0;
    virtual std::string scan() = 0;
};

// Обе возможности устройства поддерживаются.
class AllInOne final : public OfficeDevice {
public:
    explicit AllInOne(std::ostream& output) : output_(output) {}
    void print(const std::string& text) override { output_ << text << '\n'; }
    std::string scan() override { return "Scanned document"; }

private:
    std::ostream& output_;
};

void printReport(OfficeDevice& device) { device.print("Report"); }
std::string scanDocument(OfficeDevice& device) { return device.scan(); }

// Попытка подключить устройство, которое умеет только печатать.
class SimplePrinter : public OfficeDevice {
public:
    explicit SimplePrinter(std::ostream& output) : output_(output) {}
    void print(const std::string& text) override { output_ << text << '\n'; }
    // Реализовать scan невозможно: в устройстве нет сканера.

private:
    std::ostream& output_;
}; // Класс остался абстрактным из-за OfficeDevice::scan().
```

С МФУ обе функции работают корректно. В коде нет подтипа, который обещает сканирование и неожиданно бросает исключение. Проблема — в параметре `printReport`: функция использует только печать, но её контракт требует также сканирования.

## Как проявится проблема

Попытка подключить обычный принтер упирается в избыточное требование:

```cpp
// SimplePrinter printer(std::cout);
// Не компилируется: класс остался абстрактным из-за отсутствующего scan().
```

Чтобы удовлетворить текущему интерфейсу, разработчику пришлось бы придумать фиктивный `scan()`, хотя клиент печати никогда его не вызывает. Реальной потребности в этой операции у принтера нет.

Другой обычный запрос — разрешить выбирать разрешение сканирования. Изменение `scan()` затрагивает общий контракт `OfficeDevice`, от которого зависит и печать. Если определения разнесены по заголовкам, клиент печати вынужден зависеть от заголовка со сканированием и может потребовать пересборки при его изменении.

Наличие двух методов не делает интерфейс плохим само по себе. Здесь они обслуживают разные группы клиентов, а одному из них уже требуется реализация только части возможностей. Это и есть основание для разделения.

## Переписываем

Выделим роли `Printer` и `Scanner`. Каждый клиент принимает только ту роль, которой пользуется:

```cpp
class Printer {
public:
    virtual ~Printer() = default;
    virtual void print(const std::string& text) = 0;
};

class Scanner {
public:
    virtual ~Scanner() = default;
    virtual std::string scan() = 0;
};

class SimplePrinter final : public Printer {
public:
    explicit SimplePrinter(std::ostream& output) : output_(output) {}
    void print(const std::string& text) override { output_ << text << '\n'; }

private:
    std::ostream& output_;
};

// Учебная имитация устройства: отсканированное содержимое фиксировано.
class AllInOne final : public Printer, public Scanner {
public:
    explicit AllInOne(std::ostream& output) : output_(output) {}
    void print(const std::string& text) override { output_ << text << '\n'; }
    std::string scan() override { return "Scanned document"; }

private:
    std::ostream& output_;
};

void printReport(Printer& printer) { printer.print("Report"); }
std::string scanDocument(Scanner& scanner) { return scanner.scan(); }
```

Многофункциональное устройство реализует оба интерфейса, обычный принтер — только печать. Для повторного использования `printReport` больше не требуется изображать наличие сканера.

```cpp
SimplePrinter printer(std::cout);
AllInOne combined(std::cout);
printReport(printer);
printReport(combined);
std::cout << scanDocument(combined) << '\n';
// scanDocument(printer); // Не компилируется: SimplePrinter не является Scanner.
```

Здесь множественное наследование выражает две роли; общего состояния или ромба наследования нет.

Важно изменить и параметры клиентов. Разделение объявлений не даст эффекта, если `printReport` по-прежнему требует общий интерфейс со всеми возможностями.

## Что выиграли и сколько это стоит

Теперь к печати подключаются подходящие печатающие устройства. Требования к сканированию относятся к `Scanner`, его реализациям и клиентам. Для изоляции зависимостей при компиляции объявления ролей должны находиться в отдельных заголовках; в демонстрации они собраны в один файл для чтения.

Цена — два интерфейса и необходимость явно выбирать нужную роль. Выходные потоки должны жить дольше устройств, которые хранят на них ссылки.

Общий случай применения: разные клиенты одной подсистемы используют независимые наборы операций. Если всем клиентам всегда нужен один и тот же связный набор возможностей, деление каждого метода в отдельный интерфейс не приносит такого выигрыша.

**Чем отличается от SRP:** ORR/SRP касается цельности реализуемой абстракции, ISP — контрактов, от которых зависят клиенты. Одна реализация может предоставлять разным клиентам разные интерфейсы. По числу этих интерфейсов нельзя автоматически посчитать ответственности.

**Проверьте себя:** нужно ли после выделения `Printer` и `Scanner` обязательно разделить `AllInOne` на два объекта?

**Ответ:** нет. ISP разделяет доступные клиентам роли. Устройство может остаться одним объектом, реализующим обе роли.
