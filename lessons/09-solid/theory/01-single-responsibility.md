# S — Single Responsibility Principle

## Смысл принципа

**Принцип единственной ответственности (SRP)** требует, чтобы класс реализовывал одну ответственность, реализовывал её полностью и ограничивался ею. Эту же идею выражает **правило единственности абстракции (ORR)**: класс представляет одну цельную абстракцию и предоставляет достаточное для работы с ней поведение.

Полнота относится к выбранной абстракции. Например, библиотечная модель должна соблюдать правила выдачи книг, но не обязана знать формат файла, в котором сохраняется её состояние.

Границы ответственности удобно проверять через **причины изменений**. Если один класс приходится менять по требованиям разных, независимо работающих потребителей, стоит проверить, не смешались ли в нём разные абстракции. Тесно связанные требования объединяем, независимо меняющиеся разделяем.

Признаки проблемы — затруднения с выбором ясного имени, большое количество методов и зависимостей, повторяющиеся нарушения других принципов. Если методов или зависимостей стало больше 5–7, полезно остановиться и обосновать цельность класса. Это повод для анализа, а не жёсткий числовой запрет: важно понять, какие задачи обслуживают эти методы.

## Предметная ситуация

Библиотека выдаёт книги читателям. Нужно проверить, свободна ли книга, не превышен ли лимит читателя, и зарегистрировать выдачу. После операции программа сохраняет состояние, чтобы оно не потерялось при завершении работы.

В учебной библиотеке четыре книги с номерами от 1 до 4, по одному экземпляру каждой. Читателю можно выдать не больше трёх книг одновременно. Номер читателя — положительное число. В состоянии выдач записывается, кто взял каждую книгу; значение 0 означает, что книга свободна.

Правила выдачи определяет библиотека. Способ хранения зависит от устройства программы: сначала достаточно текстового файла, позже может понадобиться база данных. Это две независимо меняющиеся стороны одной программы.

## Нарушение: выдача книги одновременно сохраняет файл

Разработчик помещает всё в основной метод `Library::lendBook()`:

```cpp
class Library {
public:
    void lendBook(int readerId, int bookId, const std::string& filename) {
        if (readerId <= 0) {
            throw std::invalid_argument("Invalid reader");
        }
        const auto book = loans_.find(bookId);
        if (book == loans_.end()) {
            throw std::invalid_argument("Unknown book");
        }
        if (book->second != 0) {
            throw std::logic_error("Book is already on loan");
        }
        int borrowed = 0;
        for (const auto& loan : loans_) {
            if (loan.second == readerId) {
                ++borrowed;
            }
        }
        if (borrowed >= 3) {
            throw std::logic_error("Reader has reached the loan limit");
        }
        book->second = readerId;

        std::ofstream file;
        file.exceptions(std::ios::failbit | std::ios::badbit);
        file.open(filename);
        for (const auto& loan : loans_) {
            file << loan.first << ' ' << loan.second << '\n';
        }
        file.close();
    }

private:
    // Номер книги -> номер читателя; 0 означает, что книга свободна.
    std::map<int, int> loans_{{1, 0}, {2, 0}, {3, 0}, {4, 0}};
};
```

Сначала метод проверяет правила и меняет состояние выдач. Затем сам выбирает способ хранения: открывает файл и записывает строки вида `номер_книги номер_читателя`.

Вызов `lendBook(7, 1, "loans.txt")` выдаёт первую книгу читателю 7. В файл попадает состояние всей библиотеки:

```text
1 7
2 0
3 0
4 0
```

## Как проявится проблема

**Меняются правила выдачи.** Библиотека запрещает выдавать новые книги читателям с просроченными возвратами. В `lendBook()` потребуется добавить соответствующую проверку перед изменением состояния. Для такого расширения в модели также понадобятся сведения о сроках возврата; в текущем примере их ещё нет.

**Меняется способ хранения.** Программу переводят с текстового файла на базу данных. В том же `lendBook()` приходится заменять открытие файла и запись строк на работу с БД. При этом ни доступность книги, ни лимит читателя не изменились.

Обе задачи затрагивают основной метод выдачи. Автор изменений в хранении должен работать с методом, в котором находятся библиотечные правила, и наоборот. Зависимости от файловой системы, формата данных, а затем и клиента БД попадают в библиотечную модель.

**Нужно проверить правила отдельно.** Чтобы выполнить успешную выдачу в исходном варианте, тест вынужден предоставить имя файла и допустить запись на диск. Даже если он проверяет только состояние выдач, операция зависит от доступности файловой системы. Хотелось бы создать библиотеку в памяти, выполнить выдачи и проверить результаты, не подключая хранение.

Исходный код может правильно работать. Проблема SRP — в объединении правил выдачи и сохранения, которые имеют разные причины изменений и разные зависимости.

## Переписываем

`Library` оставим правила выдачи и состояние. В `LibraryStorage` перенесём сохранение этого состояния:

```cpp
class Library {
public:
    void lendBook(int readerId, int bookId) {
        if (readerId <= 0) {
            throw std::invalid_argument("Invalid reader");
        }
        const auto book = loans_.find(bookId);
        if (book == loans_.end()) {
            throw std::invalid_argument("Unknown book");
        }
        if (book->second != 0) {
            throw std::logic_error("Book is already on loan");
        }
        int borrowed = 0;
        for (const auto& loan : loans_) {
            if (loan.second == readerId) {
                ++borrowed;
            }
        }
        if (borrowed >= 3) {
            throw std::logic_error("Reader has reached the loan limit");
        }
        book->second = readerId;
    }

    int borrowerOf(int bookId) const { return loans_.at(bookId); }
    std::map<int, int> loans() const { return loans_; }

private:
    std::map<int, int> loans_{{1, 0}, {2, 0}, {3, 0}, {4, 0}};
};

class LibraryStorage {
public:
    void save(const Library& library, const std::string& filename) const {
        std::ofstream file;
        file.exceptions(std::ios::failbit | std::ios::badbit);
        file.open(filename);
        for (const auto& loan : library.loans()) {
            file << loan.first << ' ' << loan.second << '\n';
        }
        file.close();
    }
};
```

`Library::lendBook()` больше не принимает имя файла и не выполняет ввод-вывод. Он полностью выполняет библиотечную операцию: проверяет ограничения и регистрирует читателя, которому выдана книга.

`loans()` возвращает копию состояния выдач. Хранилище может прочитать этот снимок, но не изменить библиотеку в обход её правил. `LibraryStorage::save()` отвечает за формат записи, открытие файла и передачу ошибок сохранения вызывающему коду.

Код приложения связывает действия:

```cpp
Library library;
const LibraryStorage storage;

library.lendBook(7, 1);
storage.save(library, "loans.txt");
```

Здесь показана ветка сохранения. Загрузка состояния при запуске может быть другой операцией компонента хранения; она не должна становиться частью выдачи книги. В этом примере каталог из четырёх книг задан заранее, чтобы сосредоточиться на одной операции.

## Проверяем правила без файлов

```cpp
Library library;
library.lendBook(7, 1);
library.lendBook(7, 2);
library.lendBook(7, 3);

// library.borrowerOf(1) == 7
// library.borrowerOf(4) == 0

// library.lendBook(8, 1); // Отказ: книга уже выдана читателю 7.
// library.lendBook(7, 4); // Отказ: у читателя уже три книги.

library.lendBook(8, 4); // Другому читателю четвёртая книга доступна.
```

Для этого сценария не нужны ни путь к файлу, ни `LibraryStorage`. Неуспешная выдача оставляет состояние прежним: проверки выполняются до изменения записи о книге.

Сохранение можно проверить отдельно: подготовить библиотеку с известными выдачами, вызвать `save()` и сравнить файл с ожидаемым содержимым. В [демонстрации](../practice/srp.cpp) так проверяется, что после разделения формат и данные сохранились.

## Где теперь проходят изменения

Новое библиотечное ограничение меняет `Library`. Пока представление сохраняемого состояния остаётся прежним, код записи файла не требуется трогать.

Замена текстового файла на БД относится к компоненту хранения и к месту его подключения в приложении. Код `Library::lendBook()` при этом не должен меняться: ему не нужно знать, куда потом запишут результат. Реализация БД в этом занятии не нужна — существенна граница, за которую вынесена работа с хранением.

Если новое правило потребует сохранять дополнительные данные, например срок возврата, изменится и договор обмена состоянием. SRP не обещает, что любое требование затронет ровно один класс. Он разделяет правила выдачи и способы сохранения, чтобы одно не было встроено в реализацию другого.

## Почему в приложении остались два вызова

Приложение организует сценарий: выдать книгу, затем сохранить результат. Последовательный вызов двух компонентов не означает, что оно реализует обе ответственности. Само приложение не проверяет лимит читателя и не записывает строки в выбранном формате.

Ошибки сохранения передаются вызывающему коду исключениями. В показанном сценарии к этому моменту состояние в памяти уже изменено. Разделение ответственностей само по себе не обеспечивает откат или атомарность: если требуется гарантия «выдать и сохранить как одно действие», её нужно обеспечить отдельно. Эта особенность есть и у исходного метода, где запись файла выполняется после изменения состояния.

## Что выиграли и сколько это стоит

Библиотечные правила можно использовать и проверять в памяти. Файловый формат и механизм записи меняются в отдельном компоненте. Обязанности остаются содержательными: модель обеспечивает корректность выдачи, хранилище преобразует снимок состояния в запись и выполняет ввод-вывод.

Цена — дополнительный компонент, договор о сохраняемых данных и место, связывающее операции. Для маленькой одноразовой программы такое разделение может не окупиться. Здесь оно оправдано самостоятельными требованиями к правилам и хранению. Наследование и набор интерфейсов для этого не понадобились.

Просто вынести запись в закрытый `Library::save()` тоже можно: основной метод станет короче. Но сам класс по-прежнему будет зависеть и от правил выдачи, и от файлового формата. Такое извлечение метода улучшает читаемость, а разделение ответственности требует определить границу между компонентами.

**Проверьте себя:** стоит ли в `LibraryStorage::save()` заново проверять, не выдано ли читателю больше трёх книг?

**Ответ:** это правило библиотеки. Если продублировать его в хранении, изменение лимита потребует согласованных правок в обоих компонентах. Хранилище сохраняет допустимое состояние модели и отвечает за собственные ошибки ввода-вывода.
