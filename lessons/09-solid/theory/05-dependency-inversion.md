# D — Dependency Inversion Principle

## Смысл принципа

**Принцип инверсии зависимости:** модули высокого уровня не должны зависеть от модулей низкого уровня. И те, и другие должны зависеть от абстракций. Абстракции не должны зависеть от деталей реализации.

Высокий уровень описывает правило или алгоритм, низкий — конкретный технический способ выполнить нужное действие. Если правило напрямую связано с такой деталью, его трудно использовать с другой реализацией. Интерфейс позволяет выразить потребность правила, а детали реализуют этот договор.

## Предметная ситуация

Программа следит за температурой оборудования. При температуре выше 80 градусов нужно сообщить о перегреве. В консольном стенде сообщение печатается на экран. В приложении оператора событие должно попадать в систему уведомлений. Правило обнаружения перегрева для этих программ одинаково.

Поэтому есть причина отделить решение **когда сообщать** от технической детали **куда передать событие**. Смена канала уведомлений не должна требовать переписывать правило порога.

## Нарушение

Монитор сам выбирает конкретный способ уведомления:

```cpp
class ConsoleAlarm {
public:
    void send(int temperature) {
        std::cout << "Overheat: " << temperature << '\n';
    }
};

class TemperatureMonitor {
public:
    void checkTemperature(int temperature) {
        if (temperature > 80) {
            alarm_.send(temperature);
        }
    }

private:
    ConsoleAlarm alarm_;
};
```

`TemperatureMonitor` знает класс `ConsoleAlarm`, хранит его и вызывает его конкретный API. Правило порога связано со способом вывода.

## Как проявится проблема

Нужно отправлять сигнал в другую систему: меняется тип поля и код монитора. Нужно проверить правило без вывода в консоль: приходится перехватывать глобальный `std::cout` или менять производственный класс ради теста. В более реалистичном варианте зависимость от сети или оборудования усложнит такую проверку ещё сильнее.

Передать `ConsoleAlarm&` через конструктор было бы полезно для управления временем жизни, но зависимость от конкретного класса осталась бы. Сам факт передачи зависимости извне ещё не означает DIP.

## Переписываем

Монитор определяет минимальную потребность: сообщить температуру при перегреве. Эту потребность выразим интерфейсом `AlarmSink`, а конкретные способы сообщения реализуют его:

```cpp
// Потребность монитора: сообщить о перегреве, независимо от канала доставки.
class AlarmSink {
public:
    virtual ~AlarmSink() = default;
    virtual void notifyOverheat(int temperature) = 0;
};

class TemperatureMonitor {
public:
    explicit TemperatureMonitor(AlarmSink& alarm) : alarm_(alarm) {}

    void checkTemperature(int temperature) {
        if (temperature > 80) {
            alarm_.notifyOverheat(temperature);
        }
    }

private:
    AlarmSink& alarm_;
};

class StreamAlarm final : public AlarmSink {
public:
    explicit StreamAlarm(std::ostream& output) : output_(output) {}

    void notifyOverheat(int temperature) override {
        output_ << "Overheat: " << temperature << '\n';
    }

private:
    std::ostream& output_;
};

class RecordingAlarm final : public AlarmSink {
public:
    void notifyOverheat(int temperature) override {
        temperatures_.push_back(temperature);
    }

    const std::vector<int>& temperatures() const { return temperatures_; }

private:
    std::vector<int> temperatures_;
};
```

`RecordingAlarm` сохраняет полученные температуры, чтобы в тесте можно было проверить, когда монитор отправил уведомление. Монитор работает с ним через тот же `AlarmSink`, что и с `StreamAlarm`, и не знает, как обрабатывается событие. Сохранённые значения доступны тесту только для чтения.

## Где произошла инверсия

До исправления зависимость исходного кода была направлена так:

```text
TemperatureMonitor → ConsoleAlarm → консоль
```

После исправления:

```text
TemperatureMonitor → AlarmSink ← StreamAlarm
                         ↑
                    RecordingAlarm
```

Стрелка означает «знает объявление типа / зависит от него». Во время исполнения монитор всё ещё вызывает конкретную реализацию. Но исходный код этой реализации теперь зависит от договора `AlarmSink`, а монитор больше не зависит от `StreamAlarm`.

При разнесении по файлам `AlarmSink` следует разместить рядом с контрактами монитора, без включения заголовков конкретных каналов. Модуль реализации подключает этот контракт. Если интерфейс заставляет монитор знать детали конкретного сетевого клиента, полезная граница ещё не получилась.

## Кто выбирает реализацию и кто владеет объектами

Выбор находится в месте сборки программы:

```cpp
StreamAlarm alarm(std::cout);
TemperatureMonitor monitor(alarm);
monitor.checkTemperature(90);
```

Объекты объявлены в порядке их зависимостей. `monitor` хранит ссылку, не владеет `alarm` и должен завершить работу до его уничтожения. Аналогично `alarm` использует живой выходной поток. Здесь не требуется ни контейнер внедрения зависимостей, ни фабрика для каждого объекта.

Теперь правило можно проверить отдельно от канала:

```cpp
RecordingAlarm alarm;
TemperatureMonitor monitor(alarm);
monitor.checkTemperature(79);
monitor.checkTemperature(80);
monitor.checkTemperature(81);
// В alarm.temperatures() должно оказаться ровно одно значение: 81.
```

В [демонстрации](../practice/dip.cpp) проверяется точное содержимое записанных событий, а также текст потоковой реализации. Граница `80` включена намеренно: правило использует строгое `>`.

## Что выиграли и сколько это стоит

Один и тот же монитор работает с разными способами уведомления и тестовым объектом. Цена — интерфейс, реализации и настройка их времени жизни. Абстракция полезна на границе изменяемой детали; оборачивать каждый устойчивый тип вроде `std::string` собственным интерфейсом не требуется.

Общий случай применения: важное правило связано с внешней или изменяемой технической деталью. Интерфейс выражает потребность правила, а реализация переводит её в операции конкретного механизма.

**Чем отличается от OCP:** OCP ставит вопрос, какой модуль остаётся прежним при расширении. DIP ставит вопрос, в какую сторону направлены зависимости между правилом и деталями. В одном решении могут одновременно работать оба принципа.

**Проверьте себя:** заменяет ли `TemperatureMonitor(ConsoleAlarm&)` реализацию DIP?

**Ответ:** это внедрение конкретной зависимости. Для показанной границы DIP нужен договор, от которого зависят и монитор, и реализация канала. Внедрение через конструктор — способ передать выбранный объект.
