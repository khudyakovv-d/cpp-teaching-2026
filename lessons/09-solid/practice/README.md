# Демонстрация SOLID

Пять независимых примеров показывают код до и после переработки. Каждый находится в отдельном файле; версии разделены пространствами имён `bad` и `good`:

- [srp.cpp](srp.cpp) — правила выдачи книг и сохранение состояния библиотеки.
- [ocp.cpp](ocp.cpp) — новые тарифы без изменения общего расчёта.
- [lsp.cpp](lsp.cpp) — нарушение договора прямоугольника квадратом и изменение иерархии.
- [isp.cpp](isp.cpp) — разделение возможностей печати и сканирования.
- [dip.cpp](dip.cpp) — правило перегрева с заменяемым получателем уведомлений.

[main.cpp](main.cpp) последовательно вызывает `run()` каждого примера. Полные определения классов из конспектов совпадают с определениями в этих файлах. Дополнительный код `run()` создаёт объекты, показывает поведение и проверяет результаты.

## Сборка и запуск

Откройте эту папку в VS Code как CMake-проект и соберите цель `solid_demo`. Из терминала:

```sh
cmake -S . -B build
cmake --build build --config Debug
```

Запуск на macOS и Linux с Make или Ninja:

```sh
./build/solid_demo
```

На Windows с генератором Visual Studio:

```powershell
.\build\Debug\solid_demo.exe
```

На Windows с Ninja исполняемый файл находится в `.\build\solid_demo.exe`.

## Что именно проверяется

`check` из [check.h](check.h) бросает исключение, если условие не выполнено. `main` выводит сообщение в `std::cerr` и завершает программу с кодом `1`. При успешной демонстрации код завершения — `0`. Проверки работают и в Release, поскольку не используют отключаемый макрос `assert`.

В SRP проверяются выдача книги и совпадение сохранённых данных до и после разделения. Затем без компонента хранения проверяются отказ при повторной выдаче занятой книги, лимит в три книги и независимость лимитов разных читателей. Отдельно проверяется, что изменение модели само не переписывает файл, а ошибка сохранения сообщается вызывающему коду. В OCP проверяется сохранение двух прежних тарифов и расчёт нового. В LSP сначала подтверждается конкретное проявление дефекта: `Square` даёт `25` там, где договор `Rectangle` обещает `20`; затем проверяется исправленная иерархия. Это демонстрация обнаруженного нарушения, а не признание старого договора корректным.

В ISP исходное МФУ корректно печатает и сканирует. Обычный принтер в исходной версии остаётся абстрактным, поскольку общий интерфейс требует от него сканирования; попытка создать такой объект оставлена в комментарии. После разделения ролей проверяются печать на обоих устройствах и работа клиента сканирования. Вызов сканирования у исправленного обычного принтера также оставлен в комментарии: он должен отвергаться компилятором.

В DIP проверяется поведение при температуре ниже порога, ровно на пороге и выше него. Тестовый получатель должен записать только `81`. Отдельно проверяется текст потокового получателя. Используемый в демонстрации `std::ostringstream` — выходной поток, который сохраняет текст в памяти; `str()` возвращает накопленную строку.

В SRP файловое сохранение выполняется в новой временной папке, которая удаляется после демонстрации. Существующие пользовательские файлы не используются. Проверки библиотечных правил работают в памяти. Остальные примеры не обращаются к настоящему принтеру, датчику или внешней системе. Числовые примеры используют небольшие корректные значения, чтобы сосредоточиться на проектировании; входная валидация и защита денежной арифметики от переполнения не являются предметом занятия.

## Вопросы для обсуждения

1. В SRP уменьшите лимит читателя до двух книг. Какой компонент изменится? А какой нужно будет менять при переходе с текстового файла на БД? Почему простого извлечения `save()` в закрытый метод `Library` недостаточно для разделения ответственности?
2. В OCP добавьте тариф с фиксированной стоимостью `300`. Какие части должны измениться, а какой алгоритм останется прежним?
3. В LSP сформулируйте постусловие `setHeight`. На каком конкретно вызове квадрат нарушает его?
4. В ISP представьте, что сканер теперь поддерживает выбор разрешения. Почему клиент печати не должен зависеть от этого изменения?
5. В DIP замените вывод в поток записью события в память. Где выбирается реализация и какой код остаётся прежним?

Во всех ответах сначала назовите требование, затем изменение кода и его последствия. Добавление интерфейса само по себе ещё не обосновывает улучшение конструкции.
