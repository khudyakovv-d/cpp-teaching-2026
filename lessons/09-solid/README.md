# Занятие 9. SOLID: как оценивать устройство классов

Работающая программа может оказаться неудобной для изменений: новый вариант поведения требует правок в нескольких местах, наследник неожиданно нарушает ожидания клиента, а проверка простого правила требует запуска внешней системы. **SOLID** — пять принципов проектирования, которые помогают заметить такие зависимости и выбрать границы между частями программы.

Принцип задаёт критерий оценки решения. Паттерн описывает повторяющуюся структуру решения. Например, фабрика может помочь отделить выбор реализации от её использования; разумность самой границы оценивают по требованиям и ожидаемым изменениям.

Хороший дизайн помогает локализовать изменения требований, уменьшает стоимость сопровождения и позволяет повторно использовать части программы. Для этого нужно выделять цельные абстракции и управлять зависимостями между ними.

**Абстракция** выделяет существенное для клиента поведение объекта и задаёт его границы. **Контракт** описывает доступные клиенту операции и то, что они обещают. **Инкапсуляция** отделяет этот контракт от деталей реализации. В примерах ниже будем оценивать классы именно с этих позиций.

## Порядок разбора

Каждый принцип разбирается одинаково: **смысл → нарушение → конкретное последствие → переписывание → выигрыш и цена**. Примеры самостоятельные и используют знакомые классы, ссылки, виртуальные методы и исключения. Все варианты до и после можно собрать и запустить. В SRP основной метод выдачи книги смешивает библиотечные правила и сохранение файла; в OCP добавление варианта затрагивает устойчивый алгоритм. Для LSP непосредственно увидим нарушение поведенческого договора, а для ISP — невозможность подключить подходящее устройство из-за лишних требований интерфейса.

Материалы идут в таком порядке:

1. [S — Single Responsibility Principle](theory/01-single-responsibility.md): единственная ответственность. Выдача книги и сохранение данных зависят от разных требований.
2. [O — Open/Closed Principle](theory/02-open-closed.md): открытость/закрытость. Добавление тарифа доставки затрагивает общий расчёт заказа.
3. [L — Liskov Substitution Principle](theory/03-liskov-substitution.md): подстановка Лисковой. Изменяемый квадрат нарушает договор независимого изменения сторон прямоугольника.
4. [I — Interface Segregation Principle](theory/04-interface-segregation.md): разделение интерфейсов. Для печати отчёта интерфейс требует от устройства ещё и сканирования.
5. [D — Dependency Inversion Principle](theory/05-dependency-inversion.md): инверсия зависимости. Правило обнаружения перегрева связано с конкретным способом уведомления.
6. [Демонстрационный проект](practice/README.md): запуск, ожидаемый вывод и вопросы для обсуждения.

Примеры рассчитаны на C++20; собственные шаблоны, лямбды и дополнительные библиотеки не нужны. Для проверки результатов используется небольшой помощник `check`, который сообщает о несовпадении исключением. Это позволяет запускать демонстрацию без настройки тестового фреймворка.

## Как провести занятие

На подробный разбор всех пяти принципов стоит отвести **40–50 минут**: короткое введение, примерно 7–8 минут на каждый пример и общее обсуждение. Перед исправленным вариантом полезно остановиться и попросить студентов назвать конкретное обещание или ожидаемое изменение, которое текущая конструкция обслуживает плохо.

Если доступно **25–30 минут**, для каждого принципа покажите исходный класс, один сценарий проблемы и ключевую часть исправления. Полные определения вспомогательных классов и запуск всех проверок оставьте для самостоятельного чтения. В таком формате это обзор принципов; на подробное переписывание всего кода времени не хватит.

Примеры не требуют знакомства с условиями лабораторных. После занятия студент сможет обосновать проблему зависимости, показать последствия предполагаемого изменения и предложить конкретную переработку, сохранив нужное поведение.

## Как пользоваться принципами

Сначала сформулируйте задачу и договор, затем укажите реальное затруднение. После этого выберите переработку и проверьте, что она сохраняет нужное поведение. Наличие пяти букв не требует пяти новых интерфейсов.

Для обсуждения кода достаточно пяти вопросов:

- **S:** какую единственную абстракцию класс реализует, полна ли она и какие требования заставляют его менять?
- **O:** какую устойчивую часть придётся править при добавлении нового варианта?
- **L:** сохраняет ли подтип обещания, на которые опирается клиент базы?
- **I:** какие операции навязаны клиенту, хотя ему нужна другая роль?
- **D:** зависит ли важное правило от детали, которую хотелось бы заменять независимо?

Один пример может затрагивать несколько принципов. Разделение интерфейсов иногда одновременно исправляет нарушение подстановки, а инверсия зависимости создаёт возможность расширения. Полезно объяснять конкретную проблему и результат изменения, а не искать единственную правильную букву.
