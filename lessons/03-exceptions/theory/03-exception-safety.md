# Каким останется объект после ошибки

Представим, что программа хранит в `Vector` действующие настройки: например, лимиты для двух операций. Она получает новые значения из файла и пытается применить их. Если второе значение ошибочно, программа должна сообщить об этом пользователю. Но дальше ей нужно работать с действующими настройками. Остались ли прежние лимиты или первый уже заменён?

Ответ зависит не от `catch`, а от того, что успела сделать функция до исключения. Разберём две функции переноса значений из одного `Vector` в другой. Отрицательные числа в новых настройках запрещены.

## Менять по мере проверки

Сначала сравним размеры, затем пройдём по элементам. Допустимое значение сразу запишем в `target`:

```cpp
void copy_checked(Vector& target, const Vector& source) {
    if (target.size() != source.size()) {
        throw std::length_error("different sizes");
    }
    for (int i = 0; i < source.size(); ++i) {
        if (source[i] < 0) {
            throw std::invalid_argument("negative element");
        }
        target[i] = source[i];
    }
}
```

Оба типа ошибок объявлены в `<stdexcept>`. Предположим, `target` содержит `[1, 2]`, а `source` — `[7, -1]`. Первый элемент будет заменён на 7. На втором функция выбросит исключение. Получатель остаётся корректным, но содержит уже `[7, 2]`.

Это важно для вызывающего кода: перехватив ошибку, он продолжит работу с тем же объектом `target`. Исключение само по себе не отменяет уже выполненные присваивания. Для действующих настроек получилось бы смешение старого и нового значений. Если программа обещает оставить прежние настройки при ошибке в файле, такой способ ей не подходит.

## Сначала проверить всё

Чтобы при ошибке сохранить прежнее значение, начнём запись только после полной проверки:

```cpp
void copy_checked_strong(Vector& target, const Vector& source) {
    if (target.size() != source.size()) {
        throw std::length_error("different sizes");
    }
    for (int i = 0; i < source.size(); ++i) {
        if (source[i] < 0) {
            throw std::invalid_argument("negative element");
        }
    }
    for (int i = 0; i < source.size(); ++i) {
        target[i] = source[i];
    }
}
```

Для `source == [7, -1]` исключение возникнет в первом цикле. До записи дело не дойдёт, и `target` останется `[1, 2]`. Если проверка прошла, второй цикл записывает только `int`; такая запись исключений не выбрасывает.

Это два разных обещания функции при ошибке:

- **Базовая гарантия:** объект остаётся корректным и ресурсы не теряются, но значение может измениться. Так работает `copy_checked`.
- **Сильная гарантия:** состояние остаётся прежним. Так работает `copy_checked_strong`.
- **Гарантия отсутствия исключений:** функция не выпускает исключение наружу. Мы встретили её в [разборе `noexcept` и деструктора](02-unwinding-and-ownership.md).

Гарантия относится к состоянию **после выхода с ошибкой**. Базовая гарантия не означает, что данные совсем не менялись; сильная не обещает, что функция всегда успешно завершится. В обоих вариантах памятью своих массивов продолжают владеть объекты `Vector`, поэтому утечки из-за выхода по исключению нет.

## Как вызывающий код использует гарантию

Если при ошибке действующие настройки сохраняются, обработчик может сообщить о неудачной попытке и продолжить работу с ними:

```cpp
Vector active(2);
active[0] = 1;
active[1] = 2;

Vector proposed(2);
proposed[0] = 7;
proposed[1] = -1;

try {
    copy_checked_strong(active, proposed);
} catch (const std::invalid_argument&) {
    std::cout << "New settings rejected; old settings remain\n";
}
std::cout << active[0] << ' ' << active[1] << '\n'; // 1 2
```

Здесь `catch` отвечает только за сообщение пользователю. Старые значения сохранились благодаря тому, **как написана** `copy_checked_strong`. Если вместо неё вызвать `copy_checked`, после ошибки программа увидит `[7, 2]`. Тогда продолжать работу с `active` как с прежними настройками нельзя: вызывающему коду пришлось бы восстановить их самому или отказаться от применения новых данных целиком.

Сильная гарантия полезна при замене действующих настроек, обновлении контейнера или любой операции, после неудачи которой пользователь ожидает увидеть прежнее состояние. Базовой достаточно, когда частичный результат допустим и вызывающий код знает, как его использовать или отбросить; например, при обработке независимых элементов пакета. Важно заранее определить это поведение и не заставлять вызывающий код угадывать его по реализации.

Второй вариант даёт сильную гарантию именно потому, что после проверки оставшиеся операции для нашего `Vector` не выбрасывают исключений. Если элементы другого типа могут выбросить ошибку при копировании, одного дополнительного цикла будет недостаточно. Тогда новые данные обычно готовят отдельно и заменяют ими старые лишь после успешного завершения всей рискованной работы.

Похожий порядок есть в [копирующем присваивании учебного `Vector`](../../02-classes-and-vector/practice/vector.cpp): сначала выделяется новый массив и копируются числа, затем удаляется старый массив и заменяются поля объекта. Если подготовка нового массива завершится ошибкой, старый ещё принадлежит объекту. В нашем упражнении ошибку вызывает недопустимое значение, которую легко воспроизвести; для присваивания `Vector` поводом может быть отказ выделения памяти. Порядок действий нужен независимо от того, как часто встречается такая ошибка.

Гарантии описывают состояние объектов, с которыми работает функция. Они сами по себе не отменяют уже сделанную запись в файл или отправленный запрос: для таких действий нужно отдельно продумывать поведение при сбое.
