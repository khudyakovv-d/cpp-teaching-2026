# Как сообщить об ошибке

Программа читает размер массива из файла. Файл может не открыться, в нём может не оказаться числа, а число может быть отрицательным. Функция должна передать вызывающему коду либо размер, либо причину неудачи.

## Ошибка как результат функции

В C один из привычных способов — вернуть код состояния, а прочитанное значение записать через указатель:

```c
#include <stdio.h>

enum Status { OK, OPEN_ERROR, READ_ERROR, BAD_SIZE };

int load_size(const char* path, int* out_size) {
    FILE* file = fopen(path, "r");
    if (file == NULL) {
        return OPEN_ERROR;
    }

    int size;
    if (fscanf(file, "%d", &size) != 1) {
        fclose(file);
        return READ_ERROR;
    }
    fclose(file);

    if (size < 0) {
        return BAD_SIZE;
    }
    *out_size = size;
    return OK;
}

int prepare_size(int* out_size) {
    int status = load_size("size.txt", out_size);
    if (status != OK) {
        return status;
    }
    return OK;
}
```

Что вернёт `prepare_size()`, если в файле записано `-3`? `load_size()` вернёт `BAD_SIZE`, а `prepare_size()` проверит и передаст этот код дальше. Значение через `out_size` при ошибке не записывается, поэтому использовать его можно только после проверки статуса.

Способ работает, но у вызывающего кода появляются обязанности. Он должен проверить статус, передать его выше, если сам не знает, что делать, и освободить полученные ресурсы на каждом раннем выходе. Здесь `load_size()` закрывает файл до возврата. Если забыть проверку в `prepare_size()`, программа может продолжить работу с размером, который не был получен. При добавлении нового ресурса, например выделенного буфера, придётся проверить все пути возврата и убедиться, что буфер освобождается на каждом из них.

В C можно вернуть структуру с результатом и статусом вместо выходного параметра. Но статус всё равно нужно проверять. Кроме того, один код вроде `READ_ERROR` не всегда говорит, в каком файле и на каком этапе произошла ошибка: этот контекст нужно передавать отдельно или добавлять при возврате наверх. Проблема не в том, что код возврата «нельзя» использовать. Важно видеть, сколько мест должны согласованно соблюдать договор функции.

## Почему конструктор использует `throw`

У конструктора нашего `Vector` другой договор. После успешного `Vector values(size)` существует готовый объект. При отрицательном размере создать его нельзя, а вернуть код ошибки оператором `return` конструктор не может. Поэтому он прерывает создание исключением:

```cpp
Vector::Vector(int size) : arr_(nullptr), size_(0) {
    if (size < 0) {
        throw std::length_error("Vector size must be non-negative");
    }
    if (size > 0) {
        arr_ = new int[size]{};
    }
    size_ = size;
}
```

`throw` передаёт ошибку вызывающему коду. `std::length_error` объявлен в `<stdexcept>` и хранит сообщение, которое можно получить через `what()`. Посмотрим, как ошибка проходит через вызов функции:

```cpp
#include "vector.h"

#include <iostream>
#include <stdexcept>

void make_vector() {
    Vector values(-1);
    std::cout << "created\n";
}

int main() {
    try {
        make_vector();
        std::cout << "after call\n";
    } catch (const std::length_error& error) {
        std::cout << "error: " << error.what() << '\n';
    }
    std::cout << "continue\n";
}
```

Предскажите вывод. Конструктор выбросит исключение, поэтому строки `created` и `after call` не появятся. Выполнится подходящий `catch`, затем программа напечатает `continue`.

`try` задаёт участок кода, ошибки из которого можно обработать. Это относится и к функциям, вызванным внутри блока. После `throw` выполнение не возвращается к пропущенной строке. Если ошибок нет, все `catch` пропускаются. Исключение бросают по значению, а обычно принимают по `const` ссылке: так обработчик получает исходный объект ошибки без лишнего копирования.

## Несколько видов ошибок

После одного `try` можно написать несколько обработчиков. Например, сложение векторов разной длины выбросит `std::length_error`, а неудачное выделение памяти может выбросить `std::bad_alloc` (его объявление находится в `<new>`):

```cpp
try {
    Vector left(2);
    Vector right(3);
    Vector sum = left + right;
} catch (const std::length_error& error) {
    std::cout << "sizes: " << error.what() << '\n';
} catch (const std::bad_alloc& error) {
    std::cout << "memory: " << error.what() << '\n';
} catch (...) {
    std::cout << "other error\n";
}
```

При успешном создании `left` и `right` выполнится только первый `catch`: размеры различаются. Обработчики проверяются сверху вниз, выбирается **один** подходящий. В C++ несколько типов стандартных ошибок имеют общий базовый тип `std::exception`. Поэтому обработчик конкретной ошибки пишут раньше общего `catch (const std::exception& error)`: иначе общий обработчик перехватит её первым. Подробно наследование типов разберём на следующем занятии.

`catch (...)` принимает любое исключение, поэтому его ставят последним; он не даёт доступа к объекту ошибки. Без возможности осмысленно обработать неизвестную ошибку такой блок лучше не добавлять.

Если подходящего обработчика здесь нет, поиск продолжается выше по вызовам. При отсутствии обработчика программа завершится через `std::terminate`. Внутри `catch` можно повторно передать пойманное исключение записью `throw;`. Это пригодится во второй части: там обработчик сначала освободит ресурс, затем передаст ту же ошибку дальше. Промежуточной функции не нужен свой `catch`, если она только передаёт ошибку дальше.

## Когда удобен каждый способ

**Код возврата** хорошо подходит для ожидаемых исходов обычной операции: пользователь не ввёл число, файл не найден. Проверка находится рядом с вызовом, поэтому возможный отказ заметен при чтении. Но её нужно написать на каждом уровне, даже если промежуточная функция не может исправить ошибку. В C значение и статус приходится передавать через структуру, специальное значение или выходной параметр; специальное значение должно быть таким, чтобы его нельзя было спутать с допустимым результатом.

**Исключение** позволяет сообщить, что объект создать не удалось, и пропустить функции, которые не умеют исправить ошибку. Обработчик может находиться там, где известно, как на неё отреагировать; объект исключения несёт тип ошибки и пояснение. При этом переход управления менее заметен при чтении кода: строки после вызова могут не выполниться. Такой путь требует продумать очистку ресурсов и состояние изменяемых объектов; этим займёмся дальше. Частые ожидаемые исходы не стоит автоматически оформлять исключениями.

В Go функция может вернуть несколько значений, поэтому результат и ошибка часто возвращаются вместе. Пример ниже показывает сам принцип; `nil` означает отсутствие ошибки:

```go
package main

import (
    "fmt"
    "strconv"
)

func parseSize(text string) (int, error) {
    size, err := strconv.Atoi(text)
    if err != nil {
        return 0, err
    }
    if size < 0 {
        return 0, fmt.Errorf("negative size")
    }
    return size, nil
}

func main() {
    size, err := parseSize("-3")
    if err != nil {
        fmt.Println("error:", err)
        return
    }
    fmt.Println("size:", size)
}
```

Здесь функция возвращает и число, и `error`, а вызывающий код явно проверяет `err`. Для `"-3"` будет выведено `error: negative size`. При ошибке число `0` не считается успешным результатом: пользоваться им можно только после проверки `err`. Проверки остаются обязательными, зато для двух результатов не нужен выходной параметр. Это делает явный возврат ошибок удобным даже в современном языке; исключения не являются единственным возможным развитием после C. В Go есть `panic`, но обычные ошибки библиотек принято возвращать как значения. Подробнее это описано в [Effective Go](https://go.dev/doc/effective_go#errors).
