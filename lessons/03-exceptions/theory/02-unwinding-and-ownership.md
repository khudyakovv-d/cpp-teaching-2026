# Что происходит с ресурсами при исключении

В первой части после `throw` управление переходило к `catch`. Между ними завершаются функции и области видимости. Что происходит с уже созданными объектами?

## Локальные объекты уничтожаются

У класса `Trace` деструктор печатает имя объекта:

```cpp
#include <iostream>
#include <stdexcept>

struct Trace {
    const char* name;
    ~Trace() { std::cout << "destroy " << name << '\n'; }
};

void work() {
    Trace first{"first"};
    Trace second{"second"};
    throw std::length_error("failed");
}

int main() {
    try {
        work();
    } catch (const std::length_error&) {
        std::cout << "catch\n";
    }
}
```

Предскажите порядок строк. Программа напечатает `destroy second`, затем `destroy first` и только потом `catch`. При выходе из функции из-за исключения деструкторы уже созданных локальных объектов вызываются в обратном порядке. Это называют **раскруткой стека**.

Это правило действует для объектов, которые успели полностью создаться. Но уничтожение локального **указателя** не удаляет память по его адресу:

```cpp
void leak() {
    int* data = new int[100];
    Vector wrong(-1);    // Конструктор выбросит исключение.
    delete[] data;       // До этой строки выполнение не дойдёт.
}
```

Адрес массива хранится только в `data`. После выхода из `leak()` указателя больше нет, а массив остаётся выделенным. Перехват исключения в вызывающей функции не вернёт потерянный адрес.

## Ручная очистка и владелец

Если хранить массив за сырым указателем, придётся предусмотреть оба пути выхода:

```cpp
void manual(int size) {
    int* data = new int[100];
    try {
        Vector other(size);
    } catch (...) {
        delete[] data;
        throw;
    }
    delete[] data;
}
```

После успешного выделения массива при `size == -1` сработают `delete[]` в `catch` и повторная передача исключения через `throw;`. При допустимом размере выполнится последний `delete[]`. Если сам `new[]` не смог выделить массив, `data` ещё не получен и удалять нечего. Появится ещё один ранний выход после выделения — для него тоже потребуется очистка. Такой код можно написать правильно, но сохранять его правильность при изменениях трудно.

Мы уже написали объект, который владеет массивом: `Vector`. Его деструктор вызывает `delete[]`. Поэтому можно передать владение ему:

```cpp
void safe(int size) {
    Vector data(100);
    Vector other(size);
}
```

При `safe(-1)` конструктор `other` выбросит исключение. `other` не успел создаться, а `data` создался: его деструктор освободит массив. При обычном выходе из функции он сделает то же самое. Связь получения ресурса с созданием объекта и освобождения с его уничтожением называется **RAII**.

В языках с блоком `finally`, например Java, очистку можно поместить туда:

```java
try {
    useResource();
} finally {
    closeResource();
}
```

Блок `finally` выполняется после обычной работы и при передаче исключения дальше. В C++ такого блока нет. Для ресурса с владельцем общую очистку выполняет деструктор. Сам `catch` не заменяет её: при обычном выполнении `catch` не вызывается.

## Исключение внутри конструктора

Теперь ошибка возникает не после создания объекта, а **в его конструкторе**. Допустим, ограничение размера проверили слишком поздно:

```cpp
struct BadHolder {
    int* data;

    BadHolder(int size) : data(new int[size]) {
        if (size > 100) {
            throw std::length_error("too large");
        }
    }

    ~BadHolder() { delete[] data; }
};

struct Holder {
    Vector data;

    Holder(int size) : data(size) {
        if (size > 100) {
            throw std::length_error("too large");
        }
    }
};
```

Предположим, `new[]` в обоих случаях успешно выделил массив для `size == 101`. Затем оба конструктора выбросят исключение. Ни `BadHolder`, ни `Holder` полностью не созданы, поэтому их собственные деструкторы не вызываются. У `BadHolder` поле `data` — только адрес: массив утечёт. У `Holder` поле `data` — уже готовый объект `Vector`: его деструктор вызовется и освободит массив.

При неудачном создании объекта уничтожаются те его поля, которые успели полностью сконструироваться. Поля создаются в порядке объявления в классе и уничтожаются в обратном порядке. Это правило помогает проследить ошибку, если полей несколько; сырой указатель сам по себе владельцем памяти не становится.

Если исключение возникнет **внутри конструктора самого `Vector` после успешного выделения**, его деструктор тоже не вызовется. Тогда ресурс нужно очистить при ошибке или заранее передать уже созданному полю-владельцу. Наш текущий `Vector(int size)` сначала проверяет отрицательный размер, затем выделяет массив, а после успешного `new[]` выполняет только присваивание числа, которое не выбрасывает исключение.

Итак, проверки, не требующие ресурса, лучше делать до его получения. Это устранило бы утечку в приведённом `BadHolder`, если бы после проверки не было других операций, способных выбросить исключение. Можно было бы написать `delete[] data;` перед конкретным `throw`, но при появлении другого пути ошибки очистку потребуется добавить и там. Если после выделения ещё возможен `throw`, нужен владелец или явная очистка на **каждом** пути ошибки. Простого правила «всегда проверяй сначала» недостаточно для конструктора, который выполняет несколько действий после выделения.

## Почему деструктор не должен выбрасывать исключение

Вернёмся к `safe(-1)`. Конструктор `other` выбрасывает ошибку, и по пути к обработчику вызывается деструктор уже созданного `data`. Мы рассчитываем, что он освободит массив и завершится. А что было бы, если бы деструктор тоже передал наружу исключение? Первое исключение ещё распространяется, а во время раскрутки появляется второе. В такой ситуации программа завершается через `std::terminate`, не дойдя до обычного `catch` для ошибки конструктора.

Поэтому деструктор должен выполнять очистку, не выпуская исключений наружу. Если операция очистки сама может завершиться ошибкой, класс должен определить, как обработать её внутри деструктора. Передавать её вызывающему коду из деструктора нельзя, если деструктор должен безопасно работать при раскрутке стека.

Для функции, из которой исключение не должно выйти, в C++ есть слово `noexcept` после списка параметров:

```cpp
void release_array(int* data) noexcept {
    delete[] data;
}
```

Здесь обещание выполнимо: удаление массива `int` не выбрасывает исключений. `noexcept` относится к **выходу исключения из функции**: внутри неё можно поймать ошибку и завершиться нормально. Если исключение всё же выйдет наружу, вызывается `std::terminate`; внешний `catch` не сможет его обработать.

В объявлении нашего `Vector` написано `~Vector();` без явного `noexcept`. Для класса с полями `int*` и `int` этот деструктор и так не допускает выхода исключений; его можно было бы явно объявить как `~Vector() noexcept;`. Реализация только освобождает массив через `delete[] arr_`, поэтому обещание соблюдается.

С конструктором ситуация другая. **Исключение из конструктора допустимо:** `Vector(int size)` сообщает, что корректный объект создать не удалось. Если объявить его `noexcept`, то при `Vector(-1)` вместо перехода к `catch` программа завершится через `std::terminate`. Поэтому такое обещание ему не подходит.
