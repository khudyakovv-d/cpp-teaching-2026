# Преобразования по иерархии

Если функция вычисляет площадь фигуры, ей достаточно вызвать `shape.area()`. Виртуальная функция уже выбирает реализацию круга или прямоугольника; определять конкретный тип вручную здесь не требуется.

Другая функция может выполнять операцию, предназначенную только для кругов, и запрашивать радиус. В интерфейсе `Shape` такого метода нет. Нужно проверить, ссылается ли полученная фигура на круг, и при успехе получить доступ к его операциям. Для этого используется явное приведение типа — cast.

Начнём с уже знакомого обращения к базе, затем рассмотрим обратный переход и переход между соседними базами. Все примеры работают с полностью созданными живыми объектами.

## Тип обращения и тип объекта

Возьмём знакомую иерархию в сокращённом виде. Нужны `<numbers>` и, для вывода в следующих фрагментах, `<iostream>`.

```cpp
class Shape {
public:
    virtual ~Shape() = default;
    virtual double area() const = 0;
};

class Circle final : public Shape {
public:
    explicit Circle(double radius) : radius_(radius) {}
    double radius() const { return radius_; }
    double area() const override {
        return std::numbers::pi * radius_ * radius_;
    }
private:
    double radius_;
};

class Rectangle final : public Shape {
public:
    Rectangle(double width, double height) : width_(width), height_(height) {}
    double area() const override { return width_ * height_; }
private:
    double width_;
    double height_;
};
```

Для краткости здесь храним только размеры; проверку их допустимости уже разбирали в занятии 6.

```cpp
Circle circle(2.0);
Rectangle rectangle(3.0, 4.0);
Shape* shape = &circle;
Shape& reference = circle;
```

Тип переменной `shape` — `Shape*`. Статический тип выражений `*shape` и `reference` — `Shape`: он известен из объявления при компиляции. Динамический тип обозначаемого полиморфного объекта — `Circle`: именно такой полный объект был создан.

Через `shape` доступны члены `Shape`, поэтому `shape->radius()` не компилируется. Вызов `shape->area()` допустим и виртуально выбирает `Circle::area()`. Если затем присвоить `shape = &rectangle`, статический тип указателя останется прежним, а динамический тип объекта под ним будет `Rectangle`.

Ни ссылка, ни указатель не создают новую фигуру. Приведение указателя или ссылки тоже не превращает прямоугольник в круг: оно получает другой способ обращения к уже существующему объекту, если правила языка это позволяют.

## Вверх: от наследника к базе

В полном круге есть однозначная публичная часть `Shape`, поэтому преобразование к базе выполняется неявно:

```cpp
Circle circle(2.0);
Shape* pointer = &circle;
const Shape& reference = circle;
```

Это **восходящее преобразование**, или **upcast**. Явное приведение здесь не требуется: нужный переход разрешён правилами публичного наследования.

Важны доступность и однозначность базы. При закрытом наследовании внешнему коду такое преобразование недоступно. В обычном ромбе `TeachingAssistant*` → `Person*` неоднозначно, а путь через `Student*` выбирает конкретную часть человека. В виртуальном ромбе общая публичная `Person` доступна однозначно.

Компилятор получает указатель именно на нужную базовую часть. При нескольких базах это может требовать изменения численного адреса. Нельзя считать, что все указатели на части одного объекта имеют одинаковое представление, или подменять преобразование ручной арифметикой адресов.

## Вниз с проверкой: dynamic_cast

Из произвольного `Shape*` нельзя неявно получить `Circle*`: фигура может быть прямоугольником. Для обратного перехода нужна проверка во время работы программы. Такой переход называют **нисходящим преобразованием**, или **downcast**.

Проверку выполняет `dynamic_cast<ЦелевойТип>(выражение)`: в угловых скобках указывают тип результата. Здесь нужен `const Circle*` — указатель, через который круг нельзя изменять. При успехе он будет указывать на существующий круг, при неуспехе результатом будет `nullptr`.

Для такой проверки исходный базовый тип должен быть полиморфным — иметь хотя бы одну виртуальную функцию. В нашем `Shape` есть и виртуальный деструктор, и `area()`.

```cpp
void printRadius(const Shape* shape) {
    const Circle* circle = dynamic_cast<const Circle*>(shape);
    if (circle != nullptr) {
        std::cout << "radius = " << circle->radius() << '\n';
    } else {
        std::cout << "not a circle\n";
    }
}
```

Вызовем эту функцию с разными фигурами:

```cpp
Circle circle(2.0);
Rectangle rectangle(3.0, 4.0);
printRadius(&circle);    // radius = 2
printRadius(&rectangle); // not a circle
```

Приведение не ищет похожие поля и не вызывает конструктор `Circle`. Самого факта наследования или виртуальной базы для проверяемого спуска недостаточно: нужны виртуальные функции. Для обычного преобразования вверх, которое мы использовали раньше, они не требуются.

```cpp
Shape* empty = nullptr;
Circle* result = dynamic_cast<Circle*>(empty); // nullptr
```

Нулевой указатель обрабатывается корректно. Висячий указатель — другое дело: `dynamic_cast` не проверяет, жив ли объект. Примеры занятия работают с полностью созданными живыми объектами; правила периода конструирования и уничтожения сложнее и здесь не используются.

Для проверки используется информация о типах во время выполнения — **RTTI** (*run-time type information*). Проверку выполняет реализация C++; перечислять все возможные наследники вручную не требуется.

## Ссылка: неуспех становится исключением

У ссылки нет состояния, аналогичного `nullptr`. Поэтому неуспешный `dynamic_cast` к ссылке бросает `std::bad_cast` из `<typeinfo>`:

```cpp
void requireCircle(const Shape& shape) {
    try {
        const Circle& circle = dynamic_cast<const Circle&>(shape);
        std::cout << "required radius = " << circle.radius() << '\n';
    } catch (const std::bad_cast&) {
        std::cout << "circle required\n";
    }
}
```

Выбор определяется договором функции. Если «объект может оказаться кругом» — обычная развилка, указатель и проверка на `nullptr` выражают это прямо. Если по договору объект обязан быть кругом, ссылка позволяет сообщить нарушение исключением. Иногда ещё лучше сразу принять `const Circle&`, если общий базовый интерфейс вообще не нужен вызывающему коду.

## Вниз без проверки: static_cast

Иногда программа уже гарантирует нужный тип объекта. Тогда допустим `static_cast<ЦелевойТип>(выражение)`: он проверяет возможность преобразования **между типами** при компиляции, но не проверяет фактический тип объекта во время выполнения. В отличие от `dynamic_cast`, такой спуск не требует виртуальных функций.

В следующем примере гарантия видна рядом: `shape` связан с базовой частью живого `circle`.

```cpp
Circle circle(2.0);
Shape& shape = circle;
Circle& sameCircle = static_cast<Circle&>(shape);
std::cout << sameCircle.radius() << '\n'; // 2
```

Теперь предположим, что за базовой ссылкой оказался прямоугольник. Связь типов `Shape` и `Circle` по-прежнему позволяет написать статическое приведение, но подходящего круга в этом объекте нет. Такой спуск имеет **неопределённое поведение** (*undefined behavior*, UB): язык не задаёт допустимый результат этой операции.

```cpp
Rectangle rectangle(3.0, 4.0);
Shape& shape = rectangle;
// Circle& wrong = static_cast<Circle&>(shape); // Не выполнять: UB.
```

Ошибочным является уже само приведение. Оно не обязано вернуть `nullptr`, бросить исключение или завершить программу. Нельзя доказывать корректность по тому, что эксперимент однажды «сработал».

Для указателей принцип тот же: `static_cast<Circle*>(shapePointer)` не проверяет тип. Нулевой исходный указатель останется нулевым, но ненулевой указатель на неправильный объект не превращается в безопасный отказ.

## Между соседними базами

Вернёмся к версии `Student`, `Employee` и `TeachingAssistant` из начала второй части, пока без общей `Person`. Функция получает студента и хочет выполнить рабочую операцию, если этот студент также является сотрудником:

```cpp
void workIfEmployed(const Student& student) {
    const Employee* employee = dynamic_cast<const Employee*>(&student);
    if (employee != nullptr) {
        employee->work();
    } else {
        std::cout << "not employed\n";
    }
}
```

Это **перекрёстное преобразование**, или **cross-cast**. `Student` и `Employee` не наследуют друг друга. Проверка использует полный объект: если передан `TeachingAssistant` с обеими публичными базами, результат указывает на его часть `Employee`. У самостоятельного `Student` этой части нет, и результат будет `nullptr`.

Исходный `Student` полиморфен благодаря виртуальному деструктору. В примере части доступны публично и определяются однозначно. `dynamic_cast` не является способом произвольно обойти закрытый доступ или неоднозначность иерархии.

Прямой `static_cast<const Employee*>(&student)` не компилируется: между двумя типами нет нужной связи наследования. Если точно известен `TeachingAssistant`, можно было бы сначала спуститься к нему, затем подняться к `Employee`. Но тогда корректность первого шага снова лежит на программисте. `dynamic_cast` проверяет наличие нужной роли без привязки к имени полного класса.

## Вниз через виртуальную базу

У виртуального ромба есть дополнительное ограничение. Возьмём готовые классы из раздела [«Как оставить одну общую базовую часть»](02-multiple-inheritance-and-diamond.md#как-оставить-одну-общую-базовую-часть). В них `Student` и `Employee` виртуально наследуют `Person`, а `TeachingAssistant` наследует обе ветви. В `Person` уже есть виртуальный деструктор, поэтому этот класс полиморфен.

```cpp
TeachingAssistant assistant("Анна Смирнова");
Person* person = &assistant;
TeachingAssistant* recovered = dynamic_cast<TeachingAssistant*>(person); // &assistant
// static_cast<TeachingAssistant*>(person); // Ошибка: спуск через виртуальную базу.
```

Восходящее преобразование к общей базе допустимо, а обратный `static_cast` через виртуальную базу запрещён языком, даже если фактический тип известен. `dynamic_cast` при наличии полиморфизма умеет найти нужный объект во время выполнения.

## const и владение сохраняются

Из ссылки на неизменяемую фигуру можно получить только неизменяемый круг:

```cpp
const Circle circle(2.0);
const Shape* shape = &circle;
const Circle* found = dynamic_cast<const Circle*>(shape);
// Circle* mutableCircle = dynamic_cast<Circle*>(shape); // Ошибка: снятие const.
```

Ни `dynamic_cast`, ни `static_cast` для этих преобразований не снимают `const`. Проверка типа не даёт права менять исходный неизменяемый объект.

Преобразование указателя также **не передаёт владение**. Для следующего примера нужен `<memory>`:

```cpp
std::unique_ptr<Shape> owner = std::make_unique<Circle>(2.0);
Circle* observer = dynamic_cast<Circle*>(owner.get());
if (observer != nullptr) {
    std::cout << observer->radius() << '\n';
}
// Не делать: std::unique_ptr<Circle> secondOwner(observer);
```

`owner.get()` возвращает невладеющий указатель. Владельцем остаётся `owner`; второй `unique_ptr` на тот же объект привёл бы к повторному удалению. После `owner.reset()` прежний `observer` становится висячим, и пользоваться им нельзя. Приведение не продлевает время жизни объекта.

## Почему другие формы cast не заменяют проверку

Мы выбрали две операции с разными гарантиями: `dynamic_cast` проверяет фактический тип, а статический спуск через `static_cast` опирается на гарантию программиста. В C++ есть и другие формы приведения; для этих переходов они не дают нужной проверки.

Например, `const_cast` позволяет снять `const` в подходящем указателе или ссылке. Он не проверяет тип объекта и не выполняет спуск по иерархии. Даже после снятия `const` изменять исходный объект, который действительно объявлен неизменяемым, нельзя.

`reinterpret_cast` допускает некоторые низкоуровневые преобразования указателей, но не выполняет нужный переход к базовой части по правилам наследования. Например, у частей `Student` и `Employee` могут быть разные адреса:

```cpp
TeachingAssistant assistant; // Вариант без Person из начала второй части.
Student* student = &assistant;
// Employee* wrong = reinterpret_cast<Employee*>(student);
// wrong->work(); // Не выполнять: корректный переход к Employee не обеспечен.
Employee* correct = dynamic_cast<Employee*>(student);
```

Запись в стиле C — `(Circle*)shape` — также не выполняет проверку `dynamic_cast`. Она может скрывать статическое приведение, снятие `const` или переинтерпретацию. Для рассматриваемых переходов именованные `static_cast` и `dynamic_cast` позволяют прямо указать намерение и увидеть, где ответственность за фактический тип лежит на программисте.

**Проверьте себя:** что вернут преобразования `Shape*` → `Circle*`, если под указателем прямоугольник? Можно ли выполнить прямой `static_cast` из `Student*` в `Employee*`? Кто удаляет круг после приведения `owner.get()`?

**Ответ:** `dynamic_cast` вернёт `nullptr`; нисходящий `static_cast` имеет UB. Прямое статическое приведение соседних баз недопустимо. Кругом продолжает владеть исходный `unique_ptr`.
