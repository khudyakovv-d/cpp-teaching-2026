# Создание объекта и управление памятью

В прошлой части мы договорились: операции вектора должны поддерживать связь между указателем и размером. Теперь разберём самый первый шаг — как получить вектор, с которым уже можно работать.

## Как подготовить вектор в C

Если размер массива определяется во время выполнения, в C память для него можно выделить через `malloc`. Функция получает количество байтов и возвращает адрес выделенного участка. При нехватке памяти она возвращает нулевой указатель. Значения элементов `malloc` не задаёт — их нужно записать отдельно.

Вернёмся к структуре из первой части. Создадим вектор из трёх нулей:

```c
#include <stdlib.h>

struct Vector {
    int* arr;
    int size;
};

int main(void) {
    struct Vector v;

    v.arr = malloc(3 * sizeof(int));
    if (v.arr == NULL) {
        return 1;
    }

    v.size = 3;
    for (int i = 0; i < v.size; ++i) {
        v.arr[i] = 0;
    }

    /* Здесь вектор готов: можно работать с его элементами. */

    free(v.arr);
    return 0;
}
```

`malloc` выделяет место для трёх `int`. Саму структуру мы объявили как локальную переменную; динамически выделяем только её массив. В C результат `malloc` можно присвоить указателю `int*` без явного приведения типа.

Посмотрим на порядок действий. После `struct Vector v;` поля ещё не инициализированы. После успешного `malloc` у нас есть память для элементов, но размер ещё не установлен, а значения элементов не записаны. Только после присваивания размера и выполнения цикла получен вектор из трёх нулей.

**Выделить память и подготовить данные к использованию — разные задачи.** `malloc` решает первую. О значении поля `size` и начальном содержимом массива он ничего не знает.

## Что здесь легко забыть

Этот код корректен, но порядок действий поддерживает программист. Если не проверить результат `malloc`, при неудаче можно обратиться по нулевому указателю. Если прочитать элементы до заполнения, их значения ещё не заданы. Если забыть установить размер, другая часть программы не сможет правильно определить границы массива.

Когда векторы создаются во многих местах, повторять всю последовательность неудобно. Её можно собрать в уже знакомую функцию `vector_init`, которая проверит аргумент, выделит память и установит поля. Это хорошее решение для C: правила подготовки находятся в одном месте.

Однако само объявление `struct Vector v;` эту функцию не вызывает. Вызывающий код должен отдельно вызвать `vector_init`, проверить её результат и только потом использовать вектор. Между появлением переменной и её готовностью остаётся промежуток, в котором работать с ней как с подготовленным вектором нельзя.

Хотим связать создание переменной с её подготовкой: если создание успешно завершилось, объект уже соблюдает свои правила. Именно эту задачу в C++ решает конструктор. Проблема не в самом `malloc`, а в том, что выделение памяти, установка состояния и дальнейшее использование приходится согласовывать вручную.

## Создать объект сразу готовым к работе

В C++ начальное состояние объекта устанавливает **конструктор**. Он вызывается при создании объекта, имеет имя класса и не имеет возвращаемого типа — даже `void`.

Добавим в публичную часть класса два объявления:

```cpp
Vector();
explicit Vector(int size);
```

Это **перегрузка**: одно имя используется для функций с разными списками параметров. Компилятор выбирает подходящий вариант по аргументам вызова. Одного различия возвращаемых типов для перегрузки недостаточно.

```cpp
Vector empty;     // Конструктор без аргументов.
Vector values(3); // Конструктор с размером.
```

После успешного выполнения `Vector values(3)` конструктор уже завершил работу: можно пользоваться вектором. Отдельного вызова `vector_init` от вызывающего кода не требуется. Если создать корректный объект не удаётся, конструктор должен сообщить об ошибке; ниже увидим, как это сделать.

Не пишите `Vector empty();`, если нужна переменная: это объявление функции без параметров, возвращающей `Vector`.

Реализация конструктора без аргументов:

```cpp
Vector::Vector() {
    arr_ = nullptr;
    size_ = 0;
}
```

В теле конструктора присваиваем начальные значения полям: `arr_` получает нулевой указатель, а `size_` — ноль. К моменту завершения конструктора пустой вектор готов к работе.

`nullptr` обозначает нулевой указатель. Пустому вектору массив не нужен; обращаться к его элементам нельзя.

Для непустого вектора потребуется память:

```cpp
// vector.cpp
#include "vector.h"
#include <stdexcept>

Vector::Vector(int size) : arr_(nullptr), size_(0) {
    if (size < 0) {
        throw std::length_error("Vector size must be non-negative");
    }
    if (size > 0) {
        arr_ = new int[size]{};
    }
    size_ = size;
}
```

В этом конструкторе начальные значения полей заданы другим способом. Часть после `:` называется **списком инициализации полей**. Поля получают значения до выполнения тела конструктора. Они инициализируются в порядке объявления в классе, поэтому сохраняем тот же порядок и в списке.

Здесь роли разделены: **конструктор устанавливает состояние вектора, а `new[]` выделяет память и создаёт элементы массива**. Конструктор не заменяет средство выделения памяти — он объединяет необходимые шаги подготовки объекта.

`new int[size]{}` создаёт динамический массив. Фигурные скобки обнуляют его элементы. Без `{}` элементы типа `int` не получили бы начальных значений, и читать их до записи было бы нельзя. При размере 0 память не выделяем.

`throw` сообщает об ошибке с помощью **исключения**. `std::length_error` объявлен в `<stdexcept>`. При отрицательном размере создание прерывается: готового объекта не будет. Как принять эту ошибку в вызывающем коде, покажем в конце занятия. Обычный `new[]` при нехватке памяти тоже сообщает об ошибке исключением, а не возвращает `nullptr`.

Здесь сначала создаём пустое состояние, затем проверяем аргумент и выделяем массив. Это позволяет читать конструктор сверху вниз и не выделять память до проверки размера.

Слово `explicit` запрещает использовать конструктор для неявного преобразования числа в вектор:

```cpp
Vector a(3);       // Можно: явно создаём вектор.
Vector b{3};       // Тоже можно для нашего интерфейса.
// Vector c = 3;   // Нельзя: потребовалось бы неявное преобразование.
```

Число 3 здесь означает размер, а не вектор со значением 3. Поэтому требуем явно выражать намерение.

## Освободить память вместе с объектом

В примере на C после работы с вектором нужно было вручную вызвать `free(v.arr)`. Если после выделения памяти появится ранний `return`, вызов `free` будет пропущен. Хотим связать освобождение ресурса с завершением жизни объекта.

Добавим в класс объявление `~Vector();`. Это **деструктор** — функция завершения жизни объекта:

```cpp
Vector::~Vector() {
    delete[] arr_;
}
```

Для массива, созданного через `new[]`, нужна операция `delete[]`. Для отдельного объекта, созданного через `new`, используется `delete`. Память от `malloc` освобождают через `free`; эти пары нельзя смешивать.

`delete[] nullptr` допустим и ничего не делает. Поэтому деструктор одинаково подходит пустому и непустому вектору.

```cpp
{
    Vector a(3);
    {
        Vector b(2);
    } // Вызывается деструктор b, освобождается его массив.
} // Вызывается деструктор a, освобождается его массив.
```

Локальные объекты в этом примере имеют автоматическое время хранения: при выходе из блока их деструкторы вызываются автоматически, в обратном порядке создания. Это происходит и при выходе через `return`. При выходе из блока из-за исключения к обработчику деструкторы уже созданных локальных объектов также вызываются.

Связь «объект получил ресурс при создании и освободил при уничтожении» называется **RAII**. В нашем случае ресурс — динамический массив. Вызывающий код работает с `Vector` и не пишет отдельный вызов освобождения его массива.

## Стек и куча: где находятся данные и сколько они живут

До этого мы говорили «локальная переменная» и «динамический массив». Теперь разберём, что за этим стоит. В обычной реализации программы память для таких данных организована по-разному.

**Стек вызовов** хранит данные, связанные с выполняющимися вызовами функций. При вызове функции в нём появляется область для этого вызова — её называют кадром стека. В ней могут находиться параметры, локальные переменные и информация, необходимая для возврата к вызывающему коду.

Если `main` вызывает `process`, а `process` вызывает `calculate`, вызовы вложены друг в друга:

```text
main выполняется               main → process → calculate
                               ┌────────────────────┐
                               │ кадр calculate     │ ← текущий вызов
                               ├────────────────────┤
                               │ кадр process       │
┌────────────────────┐         ├────────────────────┤
│ кадр main          │         │ кадр main          │
└────────────────────┘         └────────────────────┘
```

После возврата из `calculate` её кадр больше не нужен, выполнение продолжается в `process`. После возврата из `process` — в `main`. Последний начавшийся вызов завершается первым: отсюда название «стек».

Обычная локальная переменная живёт до выхода из своего блока. Если это объект нашего класса, при выходе вызывается его деструктор. Вложенный блок может закончиться раньше самой функции. Отдельно освобождать память под такую переменную через `free` или `delete` нельзя — её временем жизни управляет язык.

**Кучей** обычно называют память для динамического выделения. Участок запрашивается во время выполнения через `malloc`, `new` или `new[]`. Его время жизни не привязано к возврату из функции, которая запросила память. В рассматриваемых примерах участок нужно освободить соответствующей операцией `free`, `delete` или `delete[]`.

Здесь «стек» и «куча» — модель типичной реализации. C++ задаёт правила времени жизни и хранения, но не требует помещать каждую локальную переменную именно в физический стек: компилятор может, например, держать число в регистре. Кроме того, есть глобальные и статические переменные со своими правилами. На этом занятии сравниваем обычные локальные переменные и динамически выделенные объекты.

## Локальный Vector и его массив находятся отдельно

```cpp
void useLocalVector() {
    Vector a(3);
    std::cout << a.size() << '\n'; // 3
} // Деструктор a вызывается автоматически.
```

В типичной реализации сам `a` находится на стеке. Внутри него лежат два поля: число `size_` и указатель `arr_`. Указатель — это тоже данные: он хранит адрес другого участка памяти. Сам массив не становится частью объекта только потому, что объект содержит его адрес.

Конструктор выполнил `new int[3]{}`: массив из трёх нулей находится в куче, а поле `arr_` локального объекта `a` хранит его адрес.

При выходе из функции сначала вызывается `~Vector()`. Его `delete[] arr_` освобождает массив в куче. Затем завершается уничтожение самого локального объекта. Таким образом, автоматическое уничтожение `a` запускает написанный нами код освобождения динамической памяти.

Если бы в деструкторе не было `delete[] arr_`, завершение жизни локального объекта само по себе не освободило бы массив. В начальном примере на C была такая же схема размещения: локальная структура `v` и отдельный массив от `malloc`. Только освобождение массива там явно выполнял вызывающий код.

Размер самого `Vector` не растёт вместе с числом элементов: и `Vector a(3)`, и `Vector b(1000)` содержат указатель и размер. Различается объём их отдельных массивов в куче. Поэтому `sizeof(Vector)` не включает память элементов.

## Динамический Vector: указатель, объект и массив

Можно выделить в куче и сам `Vector`:

```cpp
void useDynamicVector() {
    Vector* p = new Vector(3);
    std::cout << p->size() << '\n'; // 3
    delete p;
}
```

Здесь уже три отдельные части. Локальная переменная `p` обычно находится на стеке и хранит адрес объекта. Сам объект `Vector` находится в куче. Его поле `arr_` указывает на ещё один участок кучи — массив элементов:

```text
СТЕК                         КУЧА
┌───────────┐                ┌──────────────────┐
│ p ────────┼───────────────►│ Vector           │
└───────────┘                │ size_ = 3        │
                             │ arr_ ────────────┼─────► [0, 0, 0]
                             └──────────────────┘
```

`p->size()` вызывает метод через указатель; это то же самое, что `(*p).size()`. Размещение объекта меняется, но конструктор выполняет ту же подготовку, что и для локального `Vector a(3)`.

При `delete p` сначала вызывается деструктор `Vector`: он освобождает массив. Затем освобождается память самого объекта `Vector`. Переменная-указатель `p` при этом ещё существует до конца своего блока, но её прежнее значение больше нельзя использовать для доступа к удалённому объекту. `delete` не записывает в `p` значение `nullptr` автоматически.

Если убрать `delete p`, выход из функции завершит жизнь только локальной переменной `p`. Указатель не вызывает деструктор объекта, на который указывает. В этом примере адрес будет потерян, а объект и его массив останутся неосвобождёнными — получится **утечка памяти**.

## Почему динамическая память может пережить вызов функции

Время жизни динамического объекта можно отделить от функции, которая его создала:

```cpp
Vector* createVector() {
    return new Vector(3);
}

void useCreatedVector() {
    Vector* p = createVector();
    std::cout << p->size() << '\n'; // 3
    delete p;
}
```

`createVector` завершилась, но выделенный объект существует дальше. Она вернула его адрес вызывающему коду; в этом примере обязанность выполнить `delete` передана `useCreatedVector`.

Если бы функция вместо этого создала локальный `Vector a(3)` и вернула `&a`, после возврата объект уже был бы уничтожен. Получение его адреса не продлевает время жизни. Обращение через такой указатель было бы ошибкой.

Динамическое выделение полезно, когда нужный объём памяти становится известен во время выполнения или объект должен пережить создавший его вызов. В нашем `Vector` достаточно динамически выделять массив; сам вектор обычно удобно оставлять локальным. Так деструктор автоматически связывает время жизни массива со временем жизни его владельца.

Стек имеет ограниченный размер: очень большие локальные массивы и глубокая рекурсия могут его исчерпать. Куча тоже ограничена, и запрос памяти может завершиться неудачей. Поэтому выбор определяется нужным временем жизни и объёмом данных; размещение в куче само по себе не делает работу с памятью безопасной.

**Проверьте себя:** чем отличаются `int values[3];` и `int* values = new int[3]{};` внутри функции?

В первом случае весь массив локальный и его жизнь закончится при выходе из блока; значения элементов в этой записи ещё не заданы. Во втором случае локален только указатель, а массив выделен динамически и обнулён. Его нужно освободить через `delete[] values`. Наличие указателя не определяет размещение данных: он может хранить и адрес локального объекта.

## Чем new отличается от выделения места под объект

Теперь сравним `new Vector(3)` с выделением памяти только под поля объекта:

```cpp
// Для std::malloc и std::free нужен заголовок <cstdlib>.
void* memory = std::malloc(sizeof(Vector));
// Это не готовый Vector: его конструктор не выполнялся.
std::free(memory);
```

`malloc(sizeof(Vector))` выделяет место только для самого объекта. Даже при успешном выделении памяти никто не установил поля и не создал внутренний массив. Приведение указателя к `Vector*` тоже не вызовет конструктор. Использовать эту память как готовый `Vector` нельзя.

В выражении `new Vector(3)` указан сам тип `Vector`. Компилятору известно его устройство: какие поля входят в объект, сколько места они занимают и какие требования к их размещению нужно соблюдать. Поэтому вручную подсчитывать количество байтов не требуется.

В нашем классе внутри объекта находятся `int* arr_` и `int size_`. Память для них выделяется как для одного целого объекта. Его размер определяется `sizeof(Vector)`, но не обязательно равен сумме `sizeof(int*) + sizeof(int)`: компилятор может оставлять промежутки между полями и в конце объекта для **выравнивания**. Выравнивание задаёт требования к адресам размещения данных; обычное выражение `new` обеспечивает подходящее размещение для указанного типа.

При этом `new` учитывает именно поля, входящие в объект. Поле `arr_` занимает место под один указатель. Массив, адрес которого будет записан в этот указатель, не входит в `sizeof(Vector)` и автоматически вслед за указателем не выделяется. Если бы класс содержал поле-массив `int values[3]`, все три числа находились бы внутри объекта и учитывались бы в его размере.

Число `3` в `new Vector(3)` — аргумент конструктора, а не размер выделяемой памяти и не количество объектов `Vector`. И `new Vector(3)`, и `new Vector(1000)` создают по одному объекту одного размера. Разный объём памяти для элементов запрашивает уже конструктор.

`malloc(sizeof(Vector))` тоже получает правильный размер с учётом размещения полей: его вычисляет выражение `sizeof`. Но сама функция `malloc` принимает только число байтов и ничего не знает о типе `Vector`. Выражение `new Vector(3)` связывает выделение подходящей памяти с созданием объекта указанного типа и вызовом его конструктора.

У `new Vector(3)` другая последовательность:

```text
new Vector(3)
    → выделить память под Vector с учётом его размера и выравнивания
    → вызвать Vector(3) в этой памяти
        → выделить отдельный массив из трёх int
        → обнулить элементы и установить поля
    → вернуть Vector*, указывающий на готовый объект
```

Память для внутреннего массива выделяет код нашего конструктора. Само выражение `new` не угадывает, какие ещё ресурсы нужны классу. `std::free(memory)` освобождает память без вызова деструктора, а `delete p` завершает жизнь объекта и освобождает его память. Пары `malloc/free` и `new/delete` нельзя смешивать.

Есть и различие в обработке неудачи: `malloc` возвращает `void*`, а при нехватке памяти — нулевой указатель; обычный `new Vector(3)` возвращает `Vector*`, а при нехватке памяти выбрасывает `std::bad_alloc`. Для нашего класса принципиально то, что `new Vector(3)` включает выполнение конструктора. Здесь рассматриваем выражение `new` целиком; отдельную функцию выделения `operator new` и создание объектов в заранее выделенной памяти пока не разбираем.

**Проверьте себя:** достаточно ли заменить `malloc` на `new[]`, чтобы больше не думать об инициализации и освобождении вектора?

Нет. Выделение массива — только один шаг. Конструктор должен установить согласованные поля, а деструктор — освободить ресурс. Связать эти действия с жизнью объекта позволяет сам класс.

**Перед продолжением:** нужно ли писать `delete[]` в `main`, если массив находится внутри локального `Vector a(3)`?

Нет. Массив освобождает деструктор `a`, который вызовется при выходе из блока.
