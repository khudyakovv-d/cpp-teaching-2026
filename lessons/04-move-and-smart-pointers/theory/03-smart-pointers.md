# Умные указатели: кто отвечает за объект

В `Vector` мы сами согласовали удаление, копирование и перемещение массива. Для владения динамическими объектами стандартная библиотека предоставляет готовые классы — **умные указатели**. Они используют уже знакомый [RAII](../../03-exceptions/theory/02-unwinding-and-ownership.md): время жизни владельца управляет временем жизни ресурса.

Если объект нужен только внутри одной функции, часто достаточно обычного `Vector values(3);`. Умный указатель полезен, когда динамический объект должен жить независимо от создавшей его функции, а ответственность за него передаётся дальше или разделяется.

## Обёртка и объект — два разных объекта

Умный указатель — обычный объект класса с конструкторами, операторами и деструктором. В общих чертах он хранит адрес управляемого объекта и использует правила владения: что делать при копировании, перемещении и уничтожении самой обёртки. Перегруженные `operator*` и `operator->` дают доступ по сохранённому адресу, поэтому пользоваться обёрткой можно похоже на обычный указатель.

Для `unique_ptr` достаточно хранить указатель и способ удаления: по умолчанию для отдельного объекта используется `delete`. Для `shared_ptr` дополнительно нужна связь с общим блоком учёта владельцев. `weak_ptr` связан с этим блоком как наблюдатель. Ниже проследим, как эти различия определяют поведение их конструкторов.

Важно различать **создание обёртки** и **создание управляемого объекта**. Пустой умный указатель можно создать без объекта. Если указатель принимает уже готовый адрес, конструктор самого объекта повторно не вызывается. А функции `make_unique` и `make_shared` организуют создание нового объекта и возвращают управляющий им указатель.

## Один владелец: unique_ptr

`std::unique_ptr<Vector>` отвечает за удаление одного `Vector`. Создадим его через `std::make_unique`; оба средства объявлены в `<memory>`:

```cpp
std::unique_ptr<Vector> empty; // Создана только пустая обёртка; Vector нет.
std::unique_ptr<Vector> owner = std::make_unique<Vector>(3);
(*owner)[0] = 10;
std::cout << owner->size() << '\n'; // 3
```

`<Vector>` задаёт тип создаваемого объекта. `make_unique<Vector>(3)` выделяет для него память и вызывает **`Vector(3)`**, а затем возвращает владельца. `*owner` даёт доступ к вектору, `owner->size()` вызывает его метод. Здесь два уровня владения: `owner` отвечает за объект `Vector`, а `Vector` — за свой массив.

При выходе из области видимости вызывается деструктор `owner`. Он выполняет удаление управляемого объекта: вызывается `~Vector()`, освобождающий массив, затем освобождается память самого `Vector`. Деструктор пустого `empty` ничего не удаляет.

Вместо повторения типа слева можно писать `auto`: компилятор выведет тип из правой части. Передадим владение:

```cpp
auto first = std::make_unique<Vector>(2);
Vector* address = first.get();
// auto copy = first; // Ошибка: unique_ptr нельзя копировать.
auto second = std::move(first);
std::cout << (first == nullptr) << '\n';      // 1
std::cout << (second.get() == address) << '\n'; // 1
```

Метод `get()` возвращает адрес, не передавая владение. У `unique_ptr`, как у любого класса, возможность копирования определяется его специальными функциями. Копирование **явно запрещено**. В упрощённом виде соответствующие объявления в публичной части класса выглядят так:

```cpp
unique_ptr(const unique_ptr&) = delete;
unique_ptr& operator=(const unique_ptr&) = delete;

unique_ptr(unique_ptr&&) noexcept;
unique_ptr& operator=(unique_ptr&&) noexcept;
```

`= delete` означает, что функцию нельзя вызывать: попытка закончится ошибкой компиляции. Поэтому точнее говорить не «конструктора копирования нет», а «он объявлен удалённым». Просто не написать собственный конструктор копирования недостаточно: при подходящих условиях компилятор может объявить его сам.

Две верхние строки запрещают создание копии и копирующее присваивание. Две нижние разрешают создание перемещением и перемещающее присваивание. Именно поэтому `auto copy = first` не компилируется, а `auto second = std::move(first)` вызывает конструктор перемещения: он принимает указатель и ответственность за удаление, оставляя `first` пустым. Независимые копии адреса здесь недопустимы: оба владельца попытались бы удалить один объект.

Здесь перемещается **`unique_ptr`**, а не `Vector`: сам вектор остаётся по прежнему адресу. При присваивании `second = std::move(first)` прежний объект `second`, если он был, сначала уничтожается. А запись `*second = std::move(*first)` для двух непустых указателей перемещала бы массив между самими векторами, сохраняя оба объекта и обоих владельцев.

Пустой указатель нельзя разыменовывать. Проверка `if (owner)` показывает, есть ли объект. Непустой указатель на `Vector(0)` при этом допустим: объект существует, просто в нём нет элементов.

## Передавать объект или доступ к нему

Функции чтения достаточно ссылки. Функция, которая принимает ответственность за время жизни, получает владельца по значению:

```cpp
void print(const Vector& values) {
    std::cout << values.size() << '\n';
}

void consume(std::unique_ptr<Vector> values) {
    if (values) {
        print(*values);
    }
} // Параметр удалит объект, если не передал владение дальше.

auto owner = std::make_unique<Vector>(2);
print(*owner);              // Владение осталось у owner.
consume(std::move(owner));  // Владение передано параметру; owner пуст.
```

Без `std::move` второй вызов попытался бы скопировать `unique_ptr` и не скомпилировался. Вернуть владельца из функции можно по значению: `return std::make_unique<Vector>(2);`. Тогда за удаление будет отвечать получатель результата.

`owner.reset()` удаляет текущий объект и делает указатель пустым. Обычный указатель, ранее полученный через `get()`, после удаления станет висячим. Нельзя вызывать `delete owner.get()` или создавать второго независимого владельца из этого адреса. Метод `release()`, напротив, отдаёт адрес **без удаления** и снимает ответственность с владельца; если адрес потерян, будет утечка. Для обычной передачи владения нужен `std::move`.

Для массива существует `std::make_unique<int[]>(3)`: такой владелец освобождает память через `delete[]`. Если нужна готовая последовательность с размером, обычно удобнее `std::vector<int>`.

## Несколько владельцев: shared_ptr

Пусть набор измерений одновременно нужен окну просмотра и заданию подготовки отчёта. Любое из них может завершиться первым. Набор должен жить, пока нужен хотя бы одному, — это **совместное владение** через `std::shared_ptr`:

```cpp
auto first = std::make_shared<Vector>(2);
auto second = first;
(*second)[0] = 99;
std::cout << (*first)[0] << '\n'; // 99: один общий Vector.
first.reset();  // Объект ещё удерживает second.
second.reset(); // Последний владелец исчез — Vector уничтожается.
```

`make_shared<Vector>(2)` создаёт `Vector`, вызывая его конструктор, и общий **контрольный блок** с числом владельцев и информацией для удаления. Строка `auto second = first` вызывает **конструктор копирования `shared_ptr`**: он сохраняет связь с тем же объектом и блоком, увеличивая число владельцев. Конструктор копирования `Vector` здесь не вызывается.

В примере счётчик меняется так: 1 → 2 → 1 → 0. Деструктор непустого `shared_ptr`, как и `reset()`, уменьшает число владельцев. Только последний владелец вызывает уничтожение `Vector`. Конструктор перемещения `shared_ptr` передаёт имеющееся владение и оставляет источник пустым, не добавляя владельца и не вызывая move-конструктор `Vector`.

Таким образом, у `shared_ptr` доступны обе пары специальных функций: копирование и перемещение. При копирующем присваивании существующий указатель отпускает прежнее владение и разделяет владение источника. В отличие от `unique_ptr`, копирование здесь согласовано с удалением через общий счётчик.

Создавайте новых владельцев копированием существующего `shared_ptr`, а не из его `get()`: иначе появятся независимые контрольные блоки, и каждый попытается удалить один объект. Совместное владение требует памяти и обновления счётчика, поэтому выбирать его только ради удобного копирования указателя не стоит. Оно также не защищает содержимое объекта от одновременного изменения в разных потоках.

## Наблюдать, не удерживая: weak_ptr

Теперь окно хочет запомнить набор, но не должно продлевать его жизнь. Обычный указатель не сообщит, удалён ли объект; `shared_ptr` сам удержит его. Для наблюдения за объектом из группы `shared_ptr` есть **`weak_ptr`**.

Его метод `lock()` пытается получить временного владельца `shared_ptr`. Если объект ещё жив, результат удерживает его; если уже уничтожен — результат пуст:

```cpp
auto owner = std::make_shared<Vector>(2);
std::weak_ptr<Vector> observer = owner;
{
    auto current = observer.lock();
    if (current) {
        std::cout << current->size() << '\n'; // 2
    }
} // current уничтожается; остаётся один владелец owner.
owner.reset();
auto current = observer.lock(); // Пусто: объект уже уничтожен.
```

Создание `weak_ptr` из `shared_ptr` регистрирует наблюдателя в контрольном блоке, не увеличивая число владельцев объекта. Его копирование добавляет наблюдателя, а уничтожение убирает; конструкторы и деструктор самого `Vector` при этом не вызываются. Блок остаётся доступным наблюдателям и после уничтожения объекта, чтобы `lock()` мог вернуть пустой результат.

Поэтому разыменовать сам `weak_ptr` нельзя: сначала получите и проверьте результат `lock()`. Если бы первый `current` оставался жив, одного `owner.reset()` для удаления объекта не хватило бы.

## Зачем нужна слабая обратная связь

Если два объекта хранят `shared_ptr` друг на друга, каждый удерживает соседа. Даже после удаления внешних владельцев счётчики не достигнут нуля. Такой **цикл владения** оставит объекты в памяти.

Например, родительский узел может удерживать дочерний, а обратная связь нужна только для обращения к родителю. Сделаем её слабой:

```cpp
struct Node {
    std::shared_ptr<Node> child;
    std::weak_ptr<Node> parent;
};

auto root = std::make_shared<Node>();
root->child = std::make_shared<Node>();
root->child->parent = root;
auto leaf = root->child;

root.reset();
auto parent = leaf->parent.lock(); // Пусто: корень уничтожен.
leaf.reset(); // Теперь уничтожается дочерний узел.
```

Имя `Node` уже доступно внутри его определения, поэтому поля могут указывать на другие узлы. Корень удерживался только переменной `root`: слабое поле `parent` владельцем не считается. При уничтожении корня исчезает и его поле `child`, но дочерний узел остаётся благодаря `leaf`. После сброса `leaf` владельцев нет и у него.

Слабая связь допускает исчезновение объекта. Поэтому выбирать её нужно по смыслу отношений, а код обязан обрабатывать пустой результат `lock()`.

## Готовые владельцы и правило нуля

Если владение представлено полем подходящего типа, класс может не писать специальные функции вручную:

```cpp
class MeasurementJob {
public:
    explicit MeasurementJob(int size)
        : values_(std::make_unique<Vector>(size)) {}
private:
    std::unique_ptr<Vector> values_;
};
```

Список инициализации конструктора создаёт поле `values_`, а `make_unique` внутри вызывает конструктор `Vector(size)`. Поле уже полностью создано до входа в тело конструктора задания. Если из этого тела выйдет исключение, поле уничтожится и освободит вектор — по правилам, разобранным в занятии об исключениях.

При обычном уничтожении задания поле тоже удалит `Vector`. Автоматическое перемещение задания переместит поле; копирование будет недоступно, потому что `unique_ptr` нельзя копировать. Это **правило нуля**: управление ресурсом поручено готовому владельцу. Если добавить пользовательское объявление деструктора, автоматические move-операции уже не появятся — их придётся рассмотреть отдельно.

Готовый владелец не согласует остальные поля за вас. Например, простая замена `int*` на `unique_ptr<int[]>` в нашем `Vector` оставила бы после автоматического перемещения пустой указатель с прежним размером. Такому классу по-прежнему нужен свой алгоритм.

При выборе начните с обычного объекта. Для одного передаваемого владельца подходит `unique_ptr`, для нескольких независимых владельцев — `shared_ptr`, для наблюдения за их объектом — `weak_ptr`. Если время жизни гарантировано вызывающей стороной, для доступа достаточно ссылки или обычного указателя.

**Проверьте себя:** копируется ли `Vector` при копировании `shared_ptr<Vector>`? Почему `weak_ptr` не разыменовывается напрямую? Что произойдёт с циклом из двух `shared_ptr` после исчезновения внешних владельцев?

<details>
<summary>Ответ</summary>

Копируется только владелец, объект остаётся общим. `weak_ptr` не гарантирует существование объекта: нужен успешный `lock()`. В цикле объекты удерживают друг друга, поэтому их счётчики не достигнут нуля и объекты не уничтожатся.

</details>
